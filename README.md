# 元素丕定 — 五行元素卡牌对战原型

Unity 2D 原型，用来验证「8×8 棋盘 + 五行元素反应 + 元素牌」这套玩法能不能成立。
本文件记录**规则是怎么定的、哪些地方原表有歧义、怎么玩、怎么跑测试**。

- 工程版本：Unity **2022.3.62f3**（`ProjectSettings/ProjectVersion.txt`）
- 打开方式：Unity Hub 打开本工程，双击 `Assets/Scenes/MainMenu.unity`，按 **Play** 从主菜单进入游戏；也可直接打开 `Assets/Scenes/Game.unity`（已在 Build Settings 里）按 **Play**。
  骨架已经搭好，不用自己摆物体；想自己搭见第七节。
- ⚠ **`Game.unity` 是「补 Canvas + EventSystem」之前建的**，所以它现在还没有这两个物体 ——
  跑一次菜单 **TapGJ ▸ 在当前场景搭建/补齐骨架**（幂等，不会动已有物体）就会补上。
  做正式 uGUI 之前记得跑这一次，否则按钮点了没反应。
- ⚠ 现在 `Assets/Levels/` 里**还没有关卡资产**，所以 Play 走的是 `GameSession` 上的「开发兜底规则」随机铺盘，
  Console 会报「没有可用的关卡」。想按关卡玩：先跑一次菜单 **TapGJ ▸ 新建关卡**（见第七节）。

### 主菜单（uGUI）

`MainMenu` 是 Build Settings 中的第一场景。入口、主菜单、章节页、关卡页和弹窗都保存为可编辑的 uGUI 对象；章节与关卡卡片按配置复制场景中的模板。

- **点击开始游戏**：入口页采用参考图的山水背景、中央题字、左上适龄标识与底部提示，点击底部按钮进入主菜单。
- **开始游戏**：进入章节选择，再进入对应章节的关卡选择。默认配置对应布局图，章节数量与每章关卡数量均可独立调整。
- **关卡卡片**：显示配置中的序号、名称与目标，状态为“待开放”“待解锁”“开始”或“已通关”。已解锁的卡片点击进入对应关卡；未绑定的显示“待开放”，点击在页底显示状态和目标摘要。章节卡片显示当前配置的关卡数量。

关卡按跨章节的配置顺序解锁：首个已绑定关卡默认开放，其余需要通关前一个已绑定关卡；未绑定条目不参与解锁链。进度按关卡的 `levelId` 保存。
- **用户 / 公告 / 设置**：入口与主菜单右上方纵向排列；用户入口随排行榜暂时停用，公告显示提示，设置保留音量控制。
- **通关排行榜**：入口暂时锁定，显示锁图标和“暂未开放”，鼠标、键盘和用户入口均不能进入。排行榜面板与前 10 名行槽保留用于后续服务接入。
- **设置**：参考图的大面板中，左上依次为音效、音乐滑块，右侧为账号、帮助、关于。账号随用户入口保持未开放；帮助和关于显示说明。左上返回、底部返回游戏或 Esc 保存音量并返回原页面；设为 0 即静音，进入游戏后保留。
- **退出**：构建版退出应用；编辑器中结束 Play。

弹窗阻止背景操作；点击遮罩、关闭或 Esc 恢复原页面和焦点。返回与 Esc 依次从关卡返回章节、从章节返回主菜单、从主菜单返回入口。方向键切换按钮，Enter / 空格确认；超出可见区域的卡片支持滚轮、拖动与键盘选中后自动滚动。

**修改章节与关卡**：选中 `Assets/UI/Data/ChapterCatalog.asset`，在 Inspector 的 `Chapters` 数组增删章节，并修改每章的 `Title`、`Description`、`Levels`。`Levels` 内的 `Title` 与 `Goal` 分别是卡片名称和目标文案；把 `Assets/Levels/Level_XX.asset` 拖入该条目的 `Definition`，点击卡片就会进入这份资产指定的关卡（不要拖 `.prefab`）。`Definition` 留空时继续显示待开放。关卡资产的 `Scene Name` 默认为 `Game`，对应场景须在 Build Settings 中启用；实际玩法与胜利条件由关卡资产决定，卡片目标文案请与之保持一致。各章可有不同数量的关卡，也支持空章节；重新打开章节页会读取最新配置。不必修改卡片 Prefab 的 On Click。游戏内“下一关”的顺序仍由 `Assets/Levels/LevelCatalog.asset` 决定。

选中章节配置时，Inspector 底部的「关卡绑定检查」会统计已绑定、待开放和存在配置问题的条目。它会显示未启用或未加入构建的场景、不同关卡资产重复使用的 Level Id，以及关卡自身的布局、目标和机制配置问题；每项标明章节与关卡位置，点击「查看关卡」可跳到对应资产修改。未绑定条目属于正常的待开放状态；同一资产在多个入口复用不会报 ID 冲突。检查只读取配置，不会自动修改或绑定资产。

音频目前没有素材。将音乐片段拖到 `GameAudio/Music` 的 AudioSource（循环播放），音效通过 `GameAudio.Instance.PlayEffect(clip)` 播放，两者使用各自的音量。`GameAudio` 随场景保留，重复进入菜单时不会生成第二份。

双击 `Assets/Scenes/MainMenu.unity` 打开菜单。页面、工具按钮、滑块与卡片模板是场景实体；运行时按章节配置复制卡片，名称与目标取自配置。`Game.unity` 已保存 `GameSession`、`Board` 等完整接线，从已绑定关卡进入时会启动对局。直接打开游戏场景仍可试玩。

### 后续替换美术

普通按钮、章节卡片和关卡卡片分别使用 `Assets/UI/Prefabs/MenuButton.prefab`、`ChapterCard.prefab` 和 `LevelCard.prefab`，三者独立保存。编辑对应 Prefab 的底图、字体、图标和选中描边，会统一更新这一类；卡片的场景模板继承其 Prefab 样式，数量与文案继续从 `ChapterCatalog.asset` 读取。Logo 和按钮图标有默认隐藏的 Image 插槽，面板、卡片和滑块底图支持九宫格。素材放到 `Assets/UI/Art/`，具体位置与替换步骤见 [主菜单美术替换说明](Assets/UI/README.md)。

入口与设置页使用提供的山水参考美术，按钮和音量滑块仍是独立 uGUI 控件；参考构图按 1280 × 720 等比适配，4:3 与宽屏保留全部按钮。主菜单和章节页保留现有墨绿与暖金样式，关卡页使用去白底的卷轴和墨色纸面卡片，多出的关卡通过横向滚动查看。按钮的焦点描边是独立图层，支持鼠标、触摸和键盘反馈；章节与关卡的数量继续从配置读取。

## 一、核心流程（对应图1）

```
游戏开始 → 第 1 回合
  ├─ 准备阶段：小怪随机移动 0~3 格；相遇时按表结算 —— 相生（输家变成赢家元素）或相克（输家直接消失），
  │             同元素相遇则禁止移动（玩家不能操作）
  │             （勾了「回合事件」的关卡：每 3~6 回合会先来一条事件，见第九节）
  ├─ 抽牌阶段：自动把手牌补到上限 5 张（本来就满 5 张则一张都不抽），玩家不需要操作
  ├─ 玩家行动阶段：小怪静止、不可主动相互作用。玩家出元素牌有两个用途（图1 第 1、2 条）：
  │              · 打在**元素格**上 → 与那只小怪按图2 发生反应
  │              · 打在**空格**上   → 在该格召唤 1 个牌面元素的小怪（默认开启，可关，见第三节）
  │              玩家自行决断何时结束该回合
  ├─ 弃牌阶段：可以弃牌（每回合最多 5 张，也可以全部弃完）
  └─ 判定阶段：达成胜利条件 → 游戏结束；回合数达到上限 15 → 失败；否则进入下一回合
```

> **达成即结算**（`TapGJ.Flow.AutoFinish`）：从玩家行动阶段开始，每帧问一次「目标达成了吗」，
> 一成立就自动走完剩余阶段（弃牌阶段也不再等玩家点「结束弃牌」）直接弹结算。
> 三个例外：还有步骤动画在播、玩家在设置面板里（暂停）、阶段还没到玩家行动/弃牌。
> 这条是测试反馈「过关就卡了」之后加的 —— 以前明明已经赢了还得再点一次「结束出牌」。

一回合的推进完全由 `GameEngine` 决定，表现层只负责把 `StepRecord` 播成动画。
逻辑层与 Unity 无关（纯 C#），所以能在 EditMode 测试里几千次跑批。

### 场景分区（由场景作者摆放，不再由代码算屏幕比例）

**所有位置和尺寸都在场景里定**：棋盘多大看 `BoardView.CellSize`，摆在哪儿看 `BoardAnchor` 的 transform；
手牌整排以 `HandAnchor` 为中心；相机是你自己摆的，代码运行时不会去动它。

```
Game.unity
├─ Main Camera                  正交；构图自己调（不再被代码接管）
├─ Systems/GameSession          回合主控（board / hand / input 三个引用）+ 临时 IMGUI HUD
├─ Systems/ClickRouter          输入分发（一个相机引用）
├─ Systems/LevelLoader          关卡加载（session / levelRoot / catalog）
├─ Anchors/BoardAnchor          BoardView：棋盘中心
├─ Anchors/HandAnchor           HandView：手牌整排中心
├─ Canvas                       正式 uGUI 的落点（骨架会补 CanvasScaler + GraphicRaycaster）
├─ EventSystem                  uGUI 收点击靠它 —— 少了它按钮点不动
└─ LevelRoot                    关卡预制体的挂载点
```

> `Canvas` / `EventSystem` 是新增的：**已有的 `Game.unity` 里还没有**，
> 跑一次 **TapGJ ▸ 在当前场景搭建/补齐骨架** 就会补上（幂等）。

> 骨架的默认值（菜单生成时用）：棋盘 `CellSize 1 / CellGap 0.1`（8×8 → 8.7 世界单位）、
> `BoardAnchor (0, 1.0)`、`HandAnchor (0, -4.8)`、相机正交大小 6.5、位于 (0, 0, -10)。
> 这些只是起点，你按自己的构图改。
>
> ⚠ **旧的 `SampleScene` 已经不能玩了**：本工程不再运行时自动创建任何东西，
> 场景里没有 `GameSession` 就没有游戏。要玩就照第七节搭一个（或用菜单一键搭骨架）。

### 上手操作

| 阶段 | 操作 |
|---|---|
| 准备阶段 | 自动播放小怪移动，玩家不用操作。（有复合元素时，会先播「复合元素产生一次」再播小怪移动） |
| 抽牌阶段 | **自动**补牌到 5 张，没有按钮 |
| 玩家行动阶段 | 点**手牌**选中 → 棋盘上**绿色高亮**能打的目标格 → 点格子出牌。元素牌有两个用途：点**元素格**发生反应、点**空格**在该格**召唤**一个该元素的小怪（见第三节）；点「结束出牌 → 弃牌」结束<br>秘术牌另有一套点法（见第八节）：融合牌是「元素1 → 元素2」两段式，分解牌一步到位；**点右键（或 Esc）随时返回普通出牌状态** |
| 弃牌阶段 | 点手牌即弃掉（每回合最多 5 张）；点「结束弃牌 → 判定」结束 |
| 任意时刻 | 「重开（同种子）」复现同一局；「重开（换种子）」换一局；**「下一关 → 第 N 关」**切到目录里的下一关；**「退出游戏」**离开游戏（后两个见下面两节） |

> 现在的 HUD 是**临时 IMGUI 版**（[Hud.cs](Assets/Scripts/View/Hud.cs)），不需要任何场景对象就能跑，
> 所以在你搭好 Canvas 之前游戏依然能玩。它实现 `IGameHud`，正式 uGUI 版 `GameHud` 做好后
> **删掉这个文件就行**，`GameSession` 一行都不用改（详见第六节「游戏内 UI：IMGUI → uGUI 的替换路径」）。

### 「下一关」按钮（HUD 右侧面板）

- 按钮上直接写**下一关的名字**（`下一关 → 第 2 关`），点之前就知道要去哪一关；
  **最后一关没有下一关**，按钮置灰，不会回到第一关
- 换关 = 换关卡定义 → 重建关卡预制体与机制 → **开一局新种子**（不像「重开」是复现同一局）。
  要求固定种子的关卡（`useFixedSeed`）仍然用它自己的 `fixedSeed`
- **不写任何通关记录**：换关是导航，不是胜利（赢的那一下结算时已经写过了）
- 顶栏会显示**现在在玩哪一关**；换关后日志面板会清空（日志属于「这一局」）并留一条 `切到下一关：…`；
  胜利横幅下面还会提示「点右侧「下一关 → 第 2 关」继续」
- **什么时候灰着**：场景里没有 `LevelLoader`（开发兜底路径），或目录里**后面没有可用关卡**
  （已到末尾 / 只有当前这一关 / 全是 None 洞）→ 按钮文字直接写「下一关（没有下一关）」，不装作能点
- 播动画时不给按：换关会重建整关，正在播的步骤动画属于上一关
- 代码分工（三层，和「重开」同一条路）：数据层 `LevelCatalog.NextAfter(levelId)`（纯查找：向后查找、跳过 None 洞）
  → 流程层 `LevelLoader.GoToNextLevel()`（换关定义 + 重建 + 新种子）
  → HUD 只问 `GameSession.HasNextLevel / NextLevelName / GoToNextLevel()`

### 「退出游戏」按钮（HUD 右侧面板，在「下一关」下面）

- **两段式**：第一下按钮自己变成红色的「**确认退出游戏？**」，**第二下**才真的退。
  它和「重开」「下一关」挤在同一块面板里，误点一下整局就没了 —— 所以不做「一下就走」
- 第二下之前随时能反悔：**4 秒**内不再点、或者去点了面板上**任何一个别的**按钮（重开 / 下一关 / 结束出牌…），
  确认态立刻作废，按钮变回「退出游戏」
- **播动画时也保持可点**：这是随时能跑掉的出口，不跟别的按钮一起被 `Busy` 锁住
- **编辑器里按下去 = 结束 Play**（`Application.Quit()` 在编辑器里什么都不做 —— Play 模式跑在编辑器进程里，
  所以「点退出没反应」是它最典型的症状）；真机构建里才是真的退出进程
- 代码分工（和「下一关」一样是单向的）：HUD 只管「点了几下」（纯状态机 `Hud.QuitConfirm`），
  真正退出只走 `SceneFlow.QuitGame()` —— 由 [SceneFlow.cs](Assets/Scripts/Flow/SceneFlow.cs) 负责
  「编辑器里怎么退、构建里怎么退」（它已经是进关 / 回主界面 / 重进本关的唯一入口）
- ⚠ 它**故意不经过 `GameSession`**：退出不是「这一局」的事，不该塞进回合主控。
  以后要改成「先回主界面再退」（`MainMenu` 场景现在还没有），只动 `SceneFlow` 一处，HUD 一行不改

### ⚠ 一个必须知道的设计问题：弃牌阶段现在是空转的

抽牌阶段是「**补到 5 张**」，所以手牌永远不会超过 5 张；而弃牌阶段是「**弃到至多 5 张**」——
两者用的是同一个数字，**手牌永远满足条件，弃牌阶段一次都不会被触发**。

实测（60 局，每回合出牌不设上限）：平均弃牌 **0.02 张/局**。

要让它有意义，得动其中一条：
- 给玩家行动阶段加**每回合出牌张数上限**（推荐，见下面的调参表）
- 或者把「瓶子满自动产出卡牌」改成会突破上限，让手牌真的能超过 5 张

> 好消息是：**瓶子满产的牌确实能把手上限顶破**，那一种情况下弃牌阶段才有事可做。

## 二、反应表怎么定的（对应图2）

图2 是**按「行元素」逐行写的**。本工程把行元素当作**主动撞上去的一方**、列元素当作**被撞上的一方**。

### 统一读法（已与设计者逐句确认）

原表混用两种句式，单看一对会觉得矛盾（「与火相遇，该金元素消失」和「与水牌相遇水元素+1」到底谁赢？）。
其实两种句式就是**五行相生 / 相克两套机制**：

| 原表句式 | 机制 | 结果 |
|---|---|---|
| 「与 X 相遇 **X元素+1**」 | **相生** | 输的那个**就地变成 X**（格子占用不变） |
| 「与 X 相遇，**该 Y 元素消失**」 | **相克** | Y **直接消失**（格子空出来） |

- 同元素相遇 → 不发生任何反应，只禁止这一次移动
- 相生链：**金→水→木→火→土→金**；相克链：**金克木、木克土、土克水、水克火、火克金**
- 10 对里 5 对相生、5 对相克，每个元素都是 **2 胜 2 负**（被 2 种元素克、被 2 种元素生），没有一家独大

读法验证（设计者给的原话）：金行「与水牌相遇水元素+1」= 金生水 → **水牌打金怪时，金怪变成水怪**；
金行「与火元素/火牌相遇，该金元素消失」= 火克金 → **金怪直接消失**。

### 10 对跨元素组合的全部结果

| 组合 | 类型 | 结果 | 原表依据 |
|---|---|---|---|
| 金 × 水 | **相生** | 金 → 水 | 金行「与水牌相遇水元素+1」 |
| 水 × 木 | **相生** | 水 → 木 | 木行「与水牌相遇木元素+1」 |
| 木 × 火 | **相生** | 木 → 火 | 木行「与火牌相遇火元素+1」 |
| 火 × 土 | **相生** | 火 → 土 | 火行「与土牌相遇土元素+1」 |
| 金 × 土 | **相生** | 土 → 金 | 金行「与土牌相遇金元素+1」 |
| 金 × 木 | 相克 | 木消失（金克木） | 金行「与木元素相遇，该木元素消失」 |
| 金 × 火 | 相克 | 金消失（火克金） | 金行「与火元素/火牌相遇，该金元素消失」 |
| 木 × 土 | 相克 | 土消失（木克土） | 木行「与土元素相遇，该土元素消失」 |
| 水 × 火 | 相克 | 火消失（水克火） | 水行「与火元素相遇，该火元素消失」 |
| 水 × 土 | 相克 | 水消失（土克水） | 水行「与土元素相遇，该水元素消失」 |

**棋盘上的净效果**：
- 相生 → 元素总数**不变**（只换身份），格子仍被占着，所以主动方**停在原地不能继续走**
- 相克 → 元素总数 **−1**，格子空出来，主动方如果赢了就**占住那一格并继续走完剩余步数**

> 实现只写一处：`ReactionTable` 构造函数里的 10 行声明，而且**每行传的是「谁输」**
> （`Generate(loser, winner)` / `Overcome(loser, winner)`）。
> 早先的写法是「传赢家」，结果 **金×火 那一对被写反了**（代码里金赢、注释里火赢），
> 让金变成 3 胜 1 负的一家独大 —— 现在改成传输家 + 一条「每个元素必须 2 胜 2 负」的测试，
> 这类错误写不进去也测得出。

图2 下半部分的**复合元素**（烬、熔岩、矿晶、寒钢、灵泉）与**秘术牌**（融合牌 / 分解牌）
已经实现，见第八节「复合元素与秘术牌」。

## 三、元素小瓶子与元素牌

- 五行各有一个小瓶子，**场上每真正消失 1 个该元素的小怪，对应瓶子 +1**
  （相生不算「消失」——元素只是换了身份，所以只有相克才攒瓶子）
- 装满（默认上限 **5**）后自动产出一张**对应元素的牌**，瓶子清零

局内左下角的算盘显示这份收集进度：三点或五点门槛直接拨满下珠；十点门槛先五进位，再攒五点，元素图标闪亮后飞出对应牌并复位。事件可用 `SetBottleCapacityForRound(3)` 或 `SetBottleCapacityForRound(10)` 临时覆盖门槛，下回合恢复；机制批量充能使用 `AddBottleCharge(element, amount)`，超过门槛会逐张兑换并保留余数。
- 玩家初始随机 5 张牌

### 开不开：`Rules.BottleMode`

| 取值 | 行为 |
|---|---|
| `Enabled`（**默认**，枚举排 0） | 元素消失 → 喂瓶；满瓶产一张对应元素牌 |
| `Disabled` | 本关**没有元素瓶**：不喂瓶、不产牌、计数恒 0（`BottleFill` / `GainCard` 两条日志也不发）；但元素照样从棋盘消失，`TotalRemoved` / `RemovedCounts` 照记 |

- 老关卡资产反序列化出来是 0 = `Enabled`，所以**现有所有关卡都不受影响**。
  这也是为什么用**枚举**而不是 `bool UseBottles`：bool 在老资产上默认 `false`，会把现有的瓶子一起关掉。
  （和 `EmptyCellCardMode.Summon = 0` 是同一个兼容套路。）
- 关瓶之后「玉翁敛息」自动判**不适用**（抽到会被跳过、不占本回合），引擎的
  `ApplyBottleCapacity` 也会变成 no-op（返回 0，容量不变）。
- **第一章 5 关全部设成 `Disabled`**（章节描述里的「无元素瓶」）；**第三章起全部 `Enabled`**：第三章是教它，第四章是**叠加**（五关都留着瓶子，见第八节「机制叠加」）。
- 旧 IMGUI HUD 在关瓶时不再画瓶子条；新的 uGUI 局内 UI（`BattleGameplayHud`）本来就不画瓶子。
- 关卡面板摘要会多一句 **`无元素瓶`**，一眼看得出这一关关没关。

### 出牌规则（`Rules.CardEffect = CardAsVirtualElement`）

牌当成一个**虚拟元素**主动撞上目标格上的元素，按上面同一张表结算，所以出牌结果也只有两种：

- **相克对**：牌面元素克制目标 → 目标**直接消失**（不生成任何东西）；
  反过来（目标克制牌）时这张牌打出去场上什么都不会变 → **该次出牌被拒绝**（不消耗手牌）
- **相生对**：输的一方变成赢家元素，并且赢家元素在目标旁边 **+1**
  - 牌面元素赢 → 目标**就地变成牌面元素**，旁边再生成 1 个牌面元素
  - 目标元素赢 → 目标**不变**，牌自己变成目标元素落到旁边（即生成 1 个目标元素）
- 同元素 → 不发生反应 → 被拒绝

行 = 目标格上的元素，列 = 打出的牌；`⛔` = 打不出去：

| 目标 ↓ 牌 → | 金牌 | 木牌 | 水牌 | 火牌 | 土牌 |
|---|---|---|---|---|---|
| **金**怪 | ⛔ 同元素 | ⛔ 相克输家 | 金→水 **+**生成水 | 金消失 | 生成 1 金 |
| **木**怪 | 木消失 | ⛔ | 生成 1 木 | 木→火 **+**生成火 | ⛔ 相克输家 |
| **水**怪 | 生成 1 水 | 水→木 **+**生成木 | ⛔ | ⛔ 相克输家 | 水消失 |
| **火**怪 | ⛔ 相克输家 | 生成 1 火 | 火消失 | ⛔ | 火→土 **+**生成土 |
| **土**怪 | 土→金 **+**生成金 | 土消失 | ⛔ 相克输家 | 生成 1 土 | ⛔ |

25 格里 **15 格可出、10 格打不出**（5 个同元素 + 5 个「牌面元素是相克输家」）。

> 设计者给的验收例子：**水牌只能作用于金怪、木怪、火怪**，打不了土怪 ——
> 土克水，水牌打土怪时消失的是牌自己，场上毫无变化。上表正好推出这个结论。

> 图1 只写了「对小怪使用卡牌，视为发生作用」，没说清牌面元素与目标元素的关系。
> 如果这不是你想要的解释，把 `Rules.CardEffect` 换成 `SameElementOnly`（只能打同元素）或
> `SameElementSpawnOne`（打同元素并原地补一个）即可。

### 元素牌的第二个用途：打在空格上 = 召唤（图1 第 2 条）

> 规则原文：**「玩家可以对空的棋盘格使用卡牌，可以在该格召唤该元素小怪」**

所以一张元素牌有**两个**用途，点哪个格子决定用哪一种：

| 点哪里 | 结果 |
|---|---|
| **元素格**（上面有小怪） | 按上面那张表发生反应（原有玩法） |
| **空格**（界内、不是墙、没有占格者） | 在**该格**召唤 1 个**牌面元素**的小怪（水牌 → 水元素，位置就是点的那一格） |
| 墙格 / 复合元素占着的格子 / 棋盘外 | 两种都用不了，出牌被拒绝（不消耗手牌） |

召唤**不是**一次「相遇」，这几条是刻意的：

- **不改变场上任何已有元素** —— 不转换、不相克、不相生，只是多出一只
- **不喂小瓶子**（瓶子只认「元素从棋盘上消失」，召唤是凭空多一只）
- **不通知关卡机制**（`ILevelRule.OnEncounter` 不会收到召唤；它没有相遇）
- 但它**就是一次正常出牌**：消耗这张牌、**占每回合出牌上限**（`MaxCardsPerRound`）、
  计入 `CardsPlayedThisRound`

统计上它**单独记账**，不和相生生成混在一起：`TotalSummoned` / `SummonedOf(元素)`（`TotalSpawned` 仍然只算
「反应/复合元素产出生成」）。日志里会打一条 `打出水牌 → 召唤 1 个水元素`。

### 所有关卡固定开启空格召唤

空格召唤是基础出牌行为，不再提供关卡开关。旧关卡 / 场景数据中的 `EmptyCellCard` 字段会被忽略，
包括原先的 `Reject` 配置；选择元素牌后点击空格，始终在该格召唤对应元素的小怪。
关卡摘要和「规则与批量模拟」窗口统一显示「空格出牌 召唤」。

**平衡上要想清楚的一件事**：召唤是**凭空多一只元素**，所以

- 它让「某元素 ≥ N」「全场只剩水」这类目标更容易（想补水就补）
- 它让「清空全场」「某元素 ≤ N」这类目标更麻烦（多了一种把元素放回去的手段）
- 批量模拟里的贪心玩家（`GreedyPlayer`）**不会主动召唤**，所以第四节那些胜率数字**不受这条规则影响**；
  召唤好不好玩只能靠人工试玩（见第十节 C）
- **关卡校验也跟着改了**：像「必须都在场」那种「布局里没有它 → 永远赢不了」的判断，现在会先问
  `Rules.CardSourceFor`（这张牌能不能把该元素放到场上：空格召唤 / 相生）；
  只有**连出牌都造不出来**才算死局 —— 原来只看字符画布局，`level_02` 因此报过假问题

## 四、胜利 / 失败条件

- 失败：**回合数达到回合上限（默认 15）仍未胜利** —— 第 15 回合结束就判负
- 胜利：由关卡数据里的 **`Rules.Goal`（`GoalSpec` = 种类 + 参数）** 决定，默认按图1 原文是「**全场只剩水元素**」

`GoalKind` 一共 7 种，改数据就能换（关卡作者在 `LevelDefinition.rules.Goal` 上选）：

| 种类 | 含义 | 参数 |
|---|---|---|
| `WaterOnly` | 全场只剩水元素（**必须至少有一只水**，空场不算赢） | — |
| `SingleElement` | 全场只剩一种元素（空场也算） | — |
| `ClearBoard` | 清空全场元素 | — |
| `SurviveRounds` | 撑过若干回合 | `Rounds` |
| `ElementAtMost` | 某元素数量 ≤ N | `Target` + `TargetCount` |
| `ElementAtLeast` | 某元素数量 ≥ N | `Target` + `TargetCount` |
| `Custom` | 由关卡预制体上的机制组件判定（见第五节） | 机制自己定 |

HUD 的进度条不认种类，只消费 `GameEngine.GetGoalProgress()`（描述 + 填充比例 + 一行文字），
所以**以后加新目标不用改 HUD**（`Custom` 的目标也走这条路：机制直接提供进度数据）。

### 实测：这两个胜利条件可不可达？

用一份固定的贪心策略（`GreedyPlayer`：能打就打最有利于减少元素种类的那张牌）跑 60 局，
15 回合上限，随机种子固定。**相生/相克语义修正之后**（出牌不限张数）：

| 胜利条件 | 胜率 | 平均回合 | 平均出牌 | 终局元素种类（平均 / 最好） |
|---|---|---|---|---|
| 只剩一种元素 `SingleElement` | **47 / 60（78%）** | 8.50 | 42.4 张/局 | 1.35 / 0 |
| 只剩水元素 `WaterOnly`（图1 原文） | **20 / 60（33%）** | 12.32 | 57.3 张/局 | 2.18 / 0 |

两个要点：

- 修正语义**之前**这两个数字是 `60/60`（5.8 回合）和 `51/60`（6.2 回合）—— 旧实现是
  「输家消失 + 赢家在相邻空格生成一只自己的复制」，元素会无限增殖，同时等于给了玩家一张
  万能移除牌。改成「相生=就地转换、相克=直接湮灭」之后元素总数只持平或减少，难度回到正常区间。
- 「终局最好 = 0」= 有局把棋盘**清空**了。`SingleElement` 里空场算胜利（`distinct <= 1`）；
  `WaterOnly` 则要求场上**必须有水且全是水**，所以对它来说空场是失败 —— 那 0 出现在输掉的局里。

`WaterOnly` 明显更难（33%）：得先清掉金木火土，最后场上还得是水。贪心策略不会主动规划相生链
（土→金→水、金→水），人类玩家用它把残留"喂"成水应该能高不少。

### 调参：每回合出牌上限对胜率的影响

`Rules.MaxCardsPerRound`（0 = 不限，当前默认）。60 局 × 每档，`PlayLimitTuningTests` 会打这张表：

**胜利条件 = 只剩一种元素**

| 出牌上限 | 胜率 | 平均回合 | 平均出牌 | 平均弃牌 | 终局元素种类 |
|---|---|---|---|---|---|
| 不限（默认） | 47/60 | 8.50 | 42.43 | 0.02 | 1.35 |
| **4 张** | **53/60** | 8.05 | 30.30 | 0.02 | 0.97 |
| 3 张 | 46/60 | 9.13 | 27.03 | 0.00 | 1.30 |
| 2 张 | 47/60 | 10.58 | 20.93 | 0.02 | 1.33 |
| 1 张 | 24/60 | 14.30 | 14.27 | 0.00 | 2.02 |

**胜利条件 = 只剩水元素**

| 出牌上限 | 胜率 | 平均回合 | 平均出牌 | 平均弃牌 | 终局元素种类 |
|---|---|---|---|---|---|
| 不限（默认） | 20/60 | 12.32 | 57.28 | 0.00 | 2.18 |
| 4 张 | 28/60 | 11.38 | 39.95 | 0.02 | 1.77 |
| **3 张** | **30/60** | 11.53 | 31.92 | 0.00 | 1.58 |
| 2 张 | 27/60 | 12.67 | 24.35 | 0.00 | 1.75 |
| 1 张 | 13/60 | 14.22 | 14.22 | 0.00 | 2.35 |

结论和修正前不一样了：**语义修对之后「不限张数」已经不再是问题**（78% / 33%，不是原来的 100%）。
上限主要用来调节奏：

- **4 张**：两种条件都最好（53/60、28/60），平均 8~11 回合，出牌数从 42 降到 30
- **3 张**：水元素条件的最佳档（30/60），出牌数更少（27~32）
- **1 张**：太难（24/60、13/60），基本告别原型阶段

> 提醒：贪心策略很笨，人类玩家（会规划相生链、会留牌）胜率应该更高。
> 这张表是用来**比不同上限之间的相对难度**，不是绝对平衡目标。
>
> 当前默认仍是 `0 = 不限`（见第十一节的已知限制）。

## 五、关卡机制：每关不同的玩法（P3）

一关的差异分两种，**分别放在两个地方**：

| 想改什么 | 放哪 | 谁来做 |
|---|---|---|
| 棋盘布局、胜利目标、数值上限、起手牌、固定种子 | **关卡定义 SO**（`LevelDefinition`） | 关卡作者，纯填数据，不用写代码 |
| 「每 3 回合冒一个火元素」这类可编程机制 | **关卡预制体上的组件**（`ILevelRule`） | 写代码的人，一个机制 = 一个组件 |

机制挂在**预制体**上而不是场景里，是因为 `LevelLoader` 进关时才实例化这个预制体 ——
于是「换关卡 = 换机制」自动成立，引擎和场景都不用为某一关写任何特判。

### 可用的元素 / 可抽到的卡牌

两个多选下拉框（`ElementMask` 位掩码），就在 `LevelDefinition.rules` 里：

| 字段 | 含义 | 默认 |
|---|---|---|
| `ElementPool` | 本关**会出现**的元素 | 全部 |
| `CardPool` | 本关**能抽到**的牌 | 全部 |

`ElementPool` 是硬约束，所有产生元素的路径都受它管：

- 随机铺盘只铺池内元素（`CreepsPerElement` 是「每种**池内**元素几个」，所以元素池从 5 种减到 2 种，初始小怪总数也跟着变）
- 字符画布局里写了池外元素 → **解析期就报错**，并指出第几行第几列
- 机制 `SpawnAt` 生成池外元素 → 返回 `null`
- 出牌相生本应生成池外元素 → 记一次「出生失败」，日志里说明是「本关不用这个元素」（而不是「周围没空格」）
  （小怪之间相遇的相生不生成新元素，只就地转换，所以只有出牌那条路会走到这里）
- 手牌里的池外元素牌打不出去（`FailReason` 直接列出本关可用元素）

于是有一条可以拿来推断的不变量：**配置正确时，棋盘上永远只出现池内元素**
（有测试按回合逐步验证整局演化）。

⚠ `CardPool` 必须是 `ElementPool` 的子集。否则打出池外元素的牌发生相生时，会把棋盘上的元素
**就地变成池外元素**（相生是就地改元素，不经过「生成」那一关）。这条会被配置校验报出来。

想「开局只有金水，但玩家能靠牌把火引进来」怎么写？把火**加进 `ElementPool`**（它表示「允许出现」），
只在 `layoutText` 里不摆火 —— 初始棋盘自然没有火，而火牌能把金变成火。这就是两个字段的分工：
**`ElementPool` 管「允许出现什么」，布局管「开局摆什么」**。

> 留空（一个都没勾）会被当成「全部元素」。这是为了兼容「加这两个字段之前存的关卡/场景」：
> 那些数据反序列化出来是 0，`Rules.Validate()` 会把它修成全部，行为与加字段前逐位一致。

### 配置校验：这一关到底能不能玩

`LevelDefinition.CollectAuthoringIssues()` 收集所有已知的死局与矛盾，**三个地方共用同一套检查**：

- **关卡资产的 Inspector**：改一个字就实时刷新（[LevelDefinitionInspector.cs](Assets/Editor/LevelDefinitionInspector.cs)）
- **菜单 TapGJ ▸ 校验所有关卡**：一次看完所有关卡，外加 `levelId` 重复检查
- **LevelLoader 进关时**：有问题直接 LogError

它认得出这些（每条都有对应的失败测试）：

| 问题 | 为什么是死局 |
|---|---|
| 目标是「只剩水元素」但元素池里没有水 | 永远赢不了 |
| 要撑过 N 回合，但回合上限 < N | 第 N 回合之前就判负了 |
| 目标盯着某元素，但本关不出现它 | 数量恒为 0 → 要么开局即胜，要么永远不成立 |
| 「只剩一种元素」而元素池只有 1 种 | 开局即胜 |
| `CardPool` 里有 `ElementPool` 没有的元素 | 出牌相生会把池外元素带进棋盘 |
| 字符画行数 / 行长 / 未知字符 / 池外元素 | 布局根本铺不出来 |
| 固定起手牌里有牌池外的牌 | 自相矛盾 |
| 目标是 Custom，但关卡预制体上没有启用的机制组件 | 永远赢不了 |
| `levelId` 为空 / 目录里 id 重复 | 进度存档互相覆盖 |

规则层面的检查在 `Rules.CollectIssues()`（纯 C#、可测），关卡层面的在 `LevelDefinition` 里，
两者拼起来就是完整的「能不能玩」。**空问题列表 = 没有已知死局**，所以可以直接当断言用。

### 写一个机制

继承 `LevelRuleBehaviour`（[Mechanics/LevelRuleBehaviour.cs](Assets/Scripts/Levels/Mechanics/LevelRuleBehaviour.cs)），只覆盖关心的那几个方法：

| 钩子 | 什么时候调用 |
|---|---|
| `OnLevelStart(engine)` | 棋盘铺好、手牌发完之后（第 1 回合开始之前） |
| `OnRoundStart(engine)` | 每回合开始（第 1 回合也算） |
| `OnEncounter(engine, info)` | 任意一次元素反应**结算完之后**（此时棋盘已是最新状态） |
| `TryExtraWin(engine, out message)` | 判定阶段：额外判赢，`message` 会显示在结算横幅上 |
| `TryExtraLose(engine, out message)` | 判定阶段：额外判负 |
| `GetGoalProgress(engine)` | HUD 画进度条（返回 `default` 就没有进度条） |

挂在预制体的**子物体**上也能被收集到（`GetComponentsInChildren<ILevelRule>(true)`）；
组件被 `enabled = false` 就当成没挂。同一关可以挂多个，按挂载顺序依次调用。

`OnEncounter` 两种来源都会通知，用 `info.IsPlayerCard` 区分（小怪互撞 / 玩家出牌）：

```csharp
public override void OnEncounter(GameEngine engine, EncounterInfo info)
{
    if (!info.IsGeneration) return;   // 只要相生；info.Rule / Winner / Loser / Cell / IsDestruction…
    _count++;
}
```

⚠ 快照里的元素是**相遇当时**的元素。相生会把输家就地改成赢家，所以 `info.Loser` 一定是
「变之前」那个（实现里专门在结算前取快照，有测试钉住；不然机制会读到已经变完的元素）。

机制抛异常只会**停用它自己**（记一条日志说明已停用），不会把主流程带崩、也不会每回合刷屏。

### 机制能改棋盘（注入 API）

| API | 作用 |
|---|---|
| `engine.SpawnAt(cell, element)` | 在空格生成一只（越界 / 墙 / 已被占 → 返回 `null`，不抛异常） |
| `engine.DestroyCreep(uid)` / `DestroyCreepAt(pos, out e)` | 让某只消失（走正常移除路径，**瓶子照常 +1**，机制不绕过资源循环） |
| `engine.BlockCell(cell, true/false)` | 运行中加 / 拆墙 |
| `engine.QueueStep(record)` / `QueueNotice(text, at, element)` | 排一步给表现层播 —— 机制造成的效果也有动画，不会插队 |
| `engine.RandomEmptyCell()` | 随机空格（用引擎自己的随机源，同一个种子可复现） |

### 自定义胜利条件：`GoalKind.Custom`

第 7 种目标。选了它，**内置判定完全不参与**，胜负只由机制组件决定；
选了 `Custom` 却一个机制都没挂 → `LevelLoader` 直接报错（不会静默变成「永远赢不了」）。

这条规则是为了堵一个很坑的 bug：关卡想用自定义目标，但 `Rules.Goal` 还是默认的
`WaterOnly`，于是玩家会因为「场上只剩水」而**莫名提前获胜**。
不是 `Custom` 的时候机制只能「**加赢**」—— 内置目标先判，不满足才问机制。

胜利条件的文案与进度条也会换成机制给的那份（`GoalDescription` / `GetGoalProgress`），
所以 HUD 不需要知道这一关到底在比什么。

### 现成的两个示例

| 组件 | 演示什么 |
|---|---|
| [SpawnOnRoundRule](Assets/Scripts/Levels/Mechanics/SpawnOnRoundRule.cs) | 每 N 回合在随机空格生成元素（`OnRoundStart` + `SpawnAt` + `QueueNotice`） |
| [ReactionCountRule](Assets/Scripts/Levels/Mechanics/ReactionCountRule.cs) | 「累计 N 次相生转换」当胜利条件（`Custom` + `OnEncounter` + `TryExtraWin` + 进度条） |
| [EqualElementCountsRule](Assets/Scripts/Levels/Mechanics/EqualElementCountsRule.cs) | 「场上各种元素数量相等」当胜利条件（`requireAllPoolElements` + `tolerance`，自带配置自查） |
| [OnlyTheseElementsRule](Assets/Scripts/Levels/Mechanics/OnlyTheseElementsRule.cs) | 「场上只剩指定的那几种元素」当胜利条件（例：只剩水和火；`allowed` 多选 + `requireEachAllowedPresent`） |
| [BottleProducedRule](Assets/Scripts/Levels/Mechanics/BottleProducedRule.cs) | 「某元素的小瓶子产出 N 张牌」当胜利条件（第三章小瓶子教学；`element` + `count`） |
| [FusionCountRule](Assets/Scripts/Levels/Mechanics/FusionCountRule.cs) | 「本局累计融合 N 次」当胜利条件（第二章合成教学） |
| [DecomposeCountRule](Assets/Scripts/Levels/Mechanics/DecomposeCountRule.cs) | 「本局累计分解 N 次」当胜利条件；`requireNoComposites` 让它变成「分解掉全部复合元素」（分解五种那关）。复合元素可以是开局摆好的，也可以是玩家自己合的 |
| [ElementKindsRule](Assets/Scripts/Levels/Mechanics/ElementKindsRule.cs) | 「场上恰好剩 N 种元素」当胜利条件（不指定是哪几种；空场天然不算赢） |

> **「A 且 B」型目标**：`Rules.RequireAllWinRules`（默认 **关** = 老语义「任一机制满足即赢」）。
> 勾上之后**所有**挂着的机制都必须返回 true 才赢 —— 于是「成功合成 1 个复合元素 **且** 场上只剩两种元素」
> 就是两个小组件叠起来，不用为每种组合再写一个专用类。
> ⚠ 默认必须是关：老关卡里常有「只做进度条/提示」的机制，它永远返回 false，一开 AND 就会把那关卡成不可能赢。
>
> **目标文案和进度条都会把每一条目标写出来**（`GameEngine.CustomGoalDescription` / `CustomGoalProgress`）：
> · **左上角那行标题**（`Description`）现在把所有机制的说明连起来，连接词按语义取 ——
>   `RequireAllWinRules` 勾上（且）用「　且　」，否则（或）用「　或　」。
>   （以前是「第一个给了描述的机制说了算」，多目标关卡在 HUD 上只显示一个目标，
>   玩家以为只要做完那一件事 —— 测试反馈过这一点。）
> · **下面那行数字**（`Label`）把每条进度用全角空格连接，例如「金牌 3 / 10　木牌 9 / 10」；
>   填充比例：且 → 取**最差**的那条，或 → 取**最好**的那条，所以「进度条满了 = 要赢了」都成立。
>   （以前只报第一条，导致「两个目标里第二个差 8 张」时进度条已经满了。）
> · **通关时那句提示**（结算面板 / 日志里的 `reason`）也会把每条都写出来：只留一个「胜利：」前缀，
>   其余用「；」连接（`GameEngine.CombineWinMessages`）。以前「且」语义只取第一条 ——
>   第三章第三关「金瓶 1 张 且 木瓶 1 张」通关时只弹金瓶那句，玩家刚打完木瓶，以为提示错了。

> 关系型的胜利条件（同时看多种元素）**不要**硬塞进内置的 `GoalKind`：内置那 7 种都只盯一种元素的数量。
> 用一个 `LevelRuleBehaviour` 子类 + 把关卡 `rules.Goal` 选成 `Custom` 就够了，代价只是这一关要有一个
> 挂了该组件的关卡预制体。
>
> ⚠ 用 `OnlyTheseElementsRule` 时自己确认「要被清掉的那种元素真的清得掉」：元素池里只放
> 「允许的元素 + 要清掉的元素」，而且要清掉的必须**有牌能打它**（相克让它消失，或相生把它变成允许的元素）。
> 否则这一关永远赢不了，而配置校验**不会**替你发现这一点。

### 过渡关卡 / 剧情文本

- 数据：关卡资产上的 **`outroText`**（多行文本，留空 = 没有）。「过渡关卡」就是把剧情写在最后一关上。
- 传递：胜利那一刻 `LevelLoader.OnLevelFinished` 会把它记到
  [LevelOutro](Assets/Scripts/Flow/LevelOutro.cs)（静态、跨场景活着），失败或没有文本则清空。
- 展示：局内 UI 的结算面板（`BattleGameplayHud.OnLevelFinished`）会把 `LevelOutro.Current`
  接在胜负说明后面显示。主界面以后想用就自己读 `LevelOutro.Current` / `HasText` / `Clear()`
  —— 读完**不会自动清空**，由展示方决定什么时候清。
- ⚠ 这是一条**单向数据通道**，没有做「剧情分页 / 逐字 / 立绘」——那些都属于 UI 同学的地盘。

重开也走 `LevelLoader.RebuildLevel`（`GameSession` 通过 `ILevelHost` 回调它），
关卡预制体会被销毁重建，所以机制里的计数跟着归零 —— 不会出现「重开一局但机制还记着上一局的数」。

另外 `LevelDefinition.useFixedSeed` 能让一关**固定种子**（谜题关用），此时菜单传进来的种子会被忽略。

### 表现层的对象所有权（一条踩过坑的规则）

```
BoardView
├─ Cells/   64 × CellView    静态：底板 + 高亮 + 坐标角标 —— 一辈子不动，也不画小怪
└─ Creeps/  N × CreepView   一只小怪恰好一个对象：色块 + 元素字（元素字是它的子物体）
```

- 小怪位置只用**局部坐标**：棋盘被挪动 / 缩放时它自动跟着走，不需要任何「布局后复位」代码
- `BoardView.Sync()` 是唯一入口，以引擎为准**双向对账**：多的销毁、少的补齐、位置归位
- 动画期间按 **uid** 冻结对应小怪，Sync 不许插手（引擎里记的是这一步**结算完**的状态）
- 元素字挂在小怪下面，所以「色块在哪字就在哪」，消失 / 生成的缩放动画也自动联动

之前不是这样的：格子里放一份小怪、`_creepRoot` 下再放一份，两套并存；
而且清理代码是死代码 —— `ShowEmpty()` 先把字段置空，调用方紧接着 `if (字段 != null)` 判断，
永远进不去，于是格子留下一个**没人销毁的色块**。表现就是两个症状：
「格子有颜色但没有元素字」（孤儿对象）和「方块飞出棋盘」（那一半用的是世界坐标，不跟棋盘走）。
现在这两类都被测试钉住了，见第八节。

### 游戏内 UI：IMGUI → uGUI 的替换路径

游戏内 HUD 现在是**临时 IMGUI 版**（[Hud.cs](Assets/Scripts/View/Hud.cs)）。换正式 uGUI 之所以是**纯添加**，
是因为依赖方向是单向的：

| 方向 | 内容 |
|---|---|
| HUD → GameSession | 只调 **5 个公开方法**推进流程：`EndPlayerRound()` / `EndDiscardRound()` / `Restart()` / `RestartWithNewSeed()` / `GoToNextLevel()` |
| HUD → SceneFlow | 只有一件事：`QuitGame()`（**退出游戏不属于「这一局」**，所以不走 GameSession，见第一节「退出游戏」按钮） |
| HUD 读 | `Engine`、`ActiveRules`、`Busy`、`Banner`、`SelectedCardId`、`Log`，以及事件 `PhaseChanged` / `SelectionChanged` / `LevelStarted` / `LevelFinished` / `EventRaised` |
| GameSession → HUD | **只认识 `IGameHud` 接口**，不认识任何具体类型 |

回合状态机靠 `while (Engine.Phase == GamePhase.PlayerAction) yield return null;` 等玩家来推
（[GameSession.cs](Assets/Scripts/View/GameSession.cs)），它**根本不知道是谁推的** —— 所以换 UI 不用动流程，
`Core` / 关卡层 / `ClickRouter` 一行都不用改。

接入方式（两种都行；`Setup` 约定**必须幂等**）：

- 把实现挂在 `GameSession` **同一个物体**上 —— `Awake` 里 `GetComponents<IGameHud>()` 自动扫到
- 挂在别的物体上 —— 在自己 `Awake` 里调 `GameSession.RegisterHud(this)`

**迁移期两个 HUD 可以并存**（都会被扫到、都拿到 session）。确认新的没问题之后，删掉 `Hud.cs` 即可 ——
主控一行都不用改。

⚠ 写 uGUI 版时**不要照抄 `Hud.Setup` 里那段 `ClickRouter.ExtraBlocker` 注册**。那是给 IMGUI 打补丁用的
（IMGUI 不参与 EventSystem，只能自己报「面板这块区域别点」）。换成 uGUI 之后，
[ClickRouter](Assets/Scripts/View/ClickRouter.cs) 走 `EventSystem.current.IsPointerOverGameObject()` 就够了，
`ExtraBlocker` 保持 `null`。脚手架已经会补 `Canvas` + `EventSystem`（见第七节），
**EventSystem 缺了的表现是「按钮点了没反应」，而且不报错** —— 这是最容易查半天的一个坑。

⚠ 反应日志别用 `GameSession.DrainNotes()`：它是 pull 且**会清空队列**，两个 HUD 并存时会互抢。
uGUI 版直接订阅 `EventRaised` 做增量追加。

正式 UI 一共三块，地基都已经在：

| 屏 | 对接面 |
|---|---|
| 主菜单 / 选关 | `LevelCatalog`（关卡列表）+ `ProgressStore.IsCleared/BestRounds` + `SceneFlow.LoadLevel` |
| 游戏内 HUD | `IGameHud` + `GameSession` 的 5 个方法 + `SceneFlow.QuitGame()` + 上面那些事件（本节） |
| 结算 | `GameSession.LevelFinished`（`LevelLoader` 已经在通关时写了 `ProgressStore.MarkCleared`） |

### 美术与特效的接入口

现有棋盘和原型手牌的基础外观仍由程序化生成：颜色来自 [ElementDefs.cs](Assets/Scripts/ElementDefs.cs) 的
`Palette`，格子与卡牌的底图是运行时逐像素生成的（`BoardView.BoxSprite()`），元素字是 legacy `TextMesh`
+ Unity 内置字体，`sortingOrder` 只用 `0/1/2/3/5` 这几个硬编码值。

**唯一已经打通的美术通道是卡牌**：[HandView.CardPrefab](Assets/Scripts/View/HandView.cs) 拖了预制体就
`Instantiate` 它并用美术连好的子物体（[CardView](Assets/Scripts/View/HandView.cs) 上序列化的
`body` / `ring` / `text`），留空就回退代码生成 —— 这条双路行为有两条测试钉着（见第八节）。
格子与小怪还是纯代码生成，要做预制体的话照这个模式复制即可（`BoardView.EnsureCreepView` 里的
`new GameObject` 换成 `Instantiate`，但**别动 `Sync()` 的对账语义和 `_frozen` 的冻结窗口**）。

**棋盘反应特效的挂点选 `BoardView.PlayStep`。**
后者是在 `FlushLog()` 里发出的，而 `FlushLog()` 是在这一步**播完之后**才被调用 —— 拿它触发特效会「先炸后动」。
`PlayStep` 里的 `switch (e.Type)` 同时知道事件类型、元素、格子坐标和播放时长，才是对的挂点。
`GameEventType` 共 17 种（`Move` / `Bump` / `Transform` / `Vanish` / `Spawn` / `SpawnBlocked` /
`BottleFill` / `GainCard` / `DrawCard` / `DiscardCard` / `CompositeSpawn` / `CompositeVanish` /
`RoundEvent` / `Message` / `Win` / `Lose` / `BottleCapacityChanged`），
可以照着列一份美术需求清单；其中相生 `Transform` 只有 5 种有向转换、相克 `Vanish` 5 种。
`RoundEvent` 是回合事件的播报（见第九节），美术上应该做成一张「事件卡」而不是一行字。

⚠ **渲染管线是 Built-in**（没有 URP/HDRP，也没装 Shader Graph / VFX Graph）：
场景粒子可用 **ParticleSystem(Shuriken) + 兼容当前管线的 shader**；Canvas 卡牌消散将原包粒子离屏渲染，再用支持 UI 遮罩的材质合成。美术从其他管线带来的材质需要适配。
`Assets/sharder/` 下的 PandaShader 系列是 `UnityCG.cginc` 的 Built-in shader，能用。
`Assets/yuansupai/` 与 `Assets/sharder/` 已在本地导入，但这两个目录和目录 `.meta` **仍未提交**。卡牌成功使用或弃掉时，`HandView.Sync` 播放消散；独立局内 UI 使用 `BattleUiController.ConsumeCard`。运行资源直接引用原包预制体，实例化其中的卡面和火星粒子，保留原 shader 与溶解曲线。原相机的两处后处理引用失效，接入配置显式绑定包内泛光配置，在 HDR 离屏画面复现光晕；接入细节、画面对照及跨会话状态见 [卡牌消散接入](docs/卡牌消散接入.md)。

## 七、怎么搭游戏场景（**手工搭，这是唯一的方式**）

本工程**不在运行时创建任何东西**：场景里没有 `GameSession` 就没有游戏，漏了引用会明确报错。
这样做是为了让「拖组件」真的成立 —— 没有隐藏的兜底，你看到的就是全部。

### 接线清单（照这张表拖，一条不漏）

| 物体 | 组件 | 字段 → 拖入什么 |
|---|---|---|
| `Systems/GameSession` | `GameSession` | `board` → BoardAnchor；`hand` → HandAnchor；`input` → ClickRouter |
| `Systems/ClickRouter` | `ClickRouter` | `worldCamera` → Main Camera（正交） |
| `Systems/LevelLoader` | `LevelLoader` | `session` → GameSession；`levelRoot` → LevelRoot；`catalog` → LevelCatalog.asset（可选，或填 `inlineLevel`） |
| `Anchors/BoardAnchor` | `BoardView` | 无必需引用；`CellSize` / `CellGap` 在 Inspector 上调 |
| `Anchors/HandAnchor` | `HandView` | 无必需引用；`CardWidth` / `CardHeight` / `CardGap` / `RowWidth` 在 Inspector 上调 |
| `LevelRoot` | — | 空物体，运行时挂关卡预制体 |
| `Main Camera` | `Camera` | 无引用；Projection = **Orthographic** |

`GameSession` 上还能调：`Seed`、`StepDuration` / `StepPause`、`AnimationsEnabled`，
以及一份**开发兜底 `Rules`**（棋盘大小、每种元素数量、回合上限、胜利目标…）。
兜底规则**只在场景里没有 `LevelLoader` 时**才生效；场景里挂了 LevelLoader，规则就来自
`LevelDefinition.rules`，此时 Inspector 会把兜底那份**置灰**并告诉你规则来自哪一关
（[GameSessionInspector.cs](Assets/Editor/GameSessionInspector.cs)），Play 时还能看到实际生效的
规则摘要和当前进度。

### 三种做法

**做法 1：自己拖（推荐）**
按上表在 Hierarchy 里建物体、把组件一个个 Add Component、引用一个个拖。
搭完执行 菜单 **TapGJ ▸ 校验当前场景**，它会逐条告诉你还差什么。

**做法 2：一键搭骨架**
菜单 **TapGJ ▸ 在当前场景搭建/补齐骨架** → 建好缺失的层级并**连好全部引用**（可撤销，不写任何文件；
**幂等**：已有的物体不会被重建或移动，只补缺的组件和引用；LevelLoader 的 `catalog` 留空，自己拖或走「新建关卡」）。
它还会顺手补上 **`Canvas`（含 CanvasScaler + GraphicRaycaster）与 `EventSystem`** ——
正式 uGUI 直接往 Canvas 下面加就行。**`EventSystem` 缺了的表现是「按钮点了没反应」，而且不报错**，
所以脚手架替你把这个坑填了；手搭的话记得自己加一个。

**做法 3：连场景文件一起新建**
菜单 **TapGJ ▸ 新建 Game 场景（含骨架）** → 生成 `Assets/Scenes/Game.unity` 并加入 Build Settings。
**只在文件不存在时创建，绝不覆盖你手搭的场景。**

### 做一关的完整流程

1. 菜单 **TapGJ ▸ 新建关卡（定义 + 预制体 + 加入目录）** → 生成 `Level_N.asset` + `Level_N.prefab`，并加入 `LevelCatalog.asset`（没有会新建），顺手把目录接进当前场景的 LevelLoader。
2. 在 `LevelDefinition` 的 Inspector 里填（**面板下半部分会实时告诉你这一关有没有配错**）：
   - `layoutText`：**字符画**棋盘（`金木水火土` = 元素，`.` = 空格，`#` = 墙；第 1 行 = 棋盘最上面一行，行数 = 高度、每行长度 = 宽度；留空 = 随机铺盘）
   - `rules.ElementPool`：**本关会出现哪些元素**（多选；留空 = 全部）
   - `rules.CardPool`：**本关能抽到哪些牌**（多选；必须是元素池的子集）
   - `rules`：其余数值 —— 棋盘尺寸、每种元素几个、起手牌张数/上限、每回合出牌上限、回合上限
   - `rules.Goal`：**胜利目标**（7 种，见第四节；`Custom` = 交给机制组件判定）
   - `fixedInitialHand`：固定起手牌（留空 = 随机 `InitialHandSize` 张）
   - `useFixedSeed` / `fixedSeed`：谜题关固定种子（勾上就忽略菜单传来的种子）
   - `useEvents` / `roundEvents`：**这一关要不要随机回合事件、用哪几条**（见第九节；
     间隔在 `rules.EventIntervalMin/Max`，短关卡记得调小）
3. 在 `Level_N.prefab` 里摆局部美术（背景/装饰）——玩法数据在 SO，视觉在预制体。
4. **要可编程机制就给它 Add Component**（继承 `LevelRuleBehaviour`，见第五节）——
   挂在预制体根物体或子物体上都行，运行时会被自动收集。挂完这个预制体就
   = 「这一关的美术 + 这一关的规则」，换关自动换机制。
5. **点 Inspector 上的「Play 这一关」**（它会把这个关卡写进 LevelLoader 的 `inlineLevel` 再进 Play），
   或者直接 Play（用目录第一关），或者从主界面走 `SceneFlow.LoadLevel(...)`。
6. 发布前跑一次 **TapGJ ▸ 校验所有关卡**，确认没有死局、也没有重复的 `levelId`。

> 直接 Play 时的关卡来源优先级：**菜单传入的** → **`inlineLevel`（调试用）** → **目录第一关**。
>
> 选了 `GoalKind.Custom` 就必须挂至少一个机制组件，否则会报错 —— 这是故意的，见第五节。
>
> 不要手工往 `BoardAnchor` 下面塞格子：`BoardView` 会先生成 W×H 个格子。
> HUD 现在是 IMGUI（实现 `IGameHud`；挂在 GameSession 同一物体上会被自动扫到，挂在别处则自己
> `RegisterHud`），不需要场景对象。
>
> **摆位置时用 Gizmo 预览**：在 Scene 视图里**选中 BoardAnchor** 会画出棋盘占地 + 每个格子；
> **选中 HandAnchor** 会画出手牌整排占地 + 每张牌的位置。没进 Play 也能看到（格子/牌都是运行时才生成的，
> 这是为了相机构图不用反复 Play）。预览行列数用 `BoardView.PreviewWidth/Height`、牌数用 `HandView.PreviewCardCount` 调。

## 八、复合元素与秘术牌（图2 上半部分）

这一节是**新增的一层玩法**：5 种复合元素 + 2 种秘术牌（融合牌 / 分解牌）。

### 五种复合元素与配方

| 复合元素 | 组成（相生链上相邻的一对） | 每回合在范围内生产 |
|---|---|---|
| 烬 | 木 + 火 | 木 +4、火 +4 |
| 熔岩 | 火 + 土 | 火 +4、土 +4 |
| 矿晶 | 土 + 金 | 土 +4、金 +4 |
| 寒钢 | 金 + 水 | 金 +4、水 +4 |
| 灵泉 | 水 + 木 | 水 +4、木 +4 |

配方就是**相生链**（金→水→木→火→土→金）上的 5 对相邻元素，和原表括号里写的一一对应，**顺序无关**
（金+水 和 水+金 都行）。表只有一处声明：`FusionRecipes`（[CompositeDefinitions.cs](Assets/Scripts/Core/CompositeDefinitions.cs)）。

### 复合元素是什么

- **占棋盘一格**，但**不会移动**（准备阶段只推进元素小怪）
- **不受元素反应影响**，元素牌也打不动它 —— 只有分解牌能动它
- 它**不是元素**：不计入任何「元素数量 / 元素种类」统计，也不喂小瓶子
- 它每回合**「产生」**自己的两种组成元素各 N 份（默认 4，可调），
  产生出来的元素才按图2 的表和周围反应

### 融合牌：怎么拿到复合元素

> 规则原文：**「如果开局场上不存在复合元素，则必须通过融合牌来获得复合元素」**

- **前提**：场上**一个复合元素都没有**时融合牌才能用。已经有一个了 → 融合牌用不出去
  （代码里就是 `GameEngine.CanFuseNow`），想再融合得先用分解牌把它拆掉
- **点法**（两段式）：
  1. 左键点手牌上的**融合牌**
  2. 左键点场上第一个元素（**元素1**）→ 它周围能配对的元素被**绿色高亮**
  3. 左键点高亮的**元素2** → 合成成功，复合元素出现在**元素1 的位置**，
     两个素材都被**消耗**掉（这是消耗，不是相克湮灭，所以**不喂小瓶子**）
  - 配不上 / 不相邻 → **不消耗手牌**，只报一句原因，可以重新点元素2
  - **点右键（或 Esc）随时返回普通出牌状态**（取消选中的牌、清掉元素1 和高亮）
- **相邻 = 十字 4 格**（上下左右紧挨着）：图2 示意图给的是十字范围，
  ⚠ **斜角不算相邻** —— 斜着摆的两只元素合不了。所以「元素1」的候选只有它上、右、下、左四个邻居
  （判定就一条：`GameEngine.IsOrthogonallyAdjacent`，用曼哈顿距离 = 1 而不是切比雪夫距离 ≤ 1）
- 想改成「全盘任意两只都能合」：把 `Rules.FusionRequiresAdjacency` 关掉
- ⚠ 注意别和**复合元素自己的产生范围**搞混：`Rules.CompositeRange` 是**正方形**（默认 1 = 周围 8 格），
  它管的是「复合元素往哪些格子产元素」，和融合的相邻判定是两回事

### 分解牌

- 点分解牌 → 点上场的**复合元素** → 它从棋盘上消失，并**给回两张对应元素的元素牌**
  （寒钢 → 一张金牌 + 一张水牌）
- 它**不占**每回合出牌上限：它不产出元素，是纯解场牌（代价是消耗一张手牌）
- 拆完之后场上又「没有复合元素」了 → 融合牌重新可用

### 复合元素的效果什么时候生效

- **融合当回合立刻生效一次**（图2 的要求），之后**每回合开始时生效一次**
- 生效顺序：**先复合元素产生，再小怪移动** —— 这样产出的元素本回合就能正常参与移动/相遇
- 产生范围：切比雪夫距离 ≤ `Rules.CompositeRange`（默认 1 = 紧邻 8 格）。⚠ 是**正方形**，
  和融合的「十字相邻」不是一回事（见上面融合牌那一节）
- 产生时优先落在**范围内已被元素占着的格子**上 → 立刻按图2 的表反应一次
  （这就是原表那句「**可与范围内已有的元素产生反应**」）；
  范围内一个空格都没有才记一次「出生失败」，**不会把元素丢到范围外**
  （一轮产生里，同一份元素最多换到范围内的另一个空格，**绝不会越出范围**）
- 产出也受 `ElementPool` 硬约束：组成元素不在本关元素池里就产不出来（会记一条说明）

#### 取格的确定规则（实现细节，但会直接影响可复现性）

0. **同一批产出先把空格「预约」掉** —— 这一批里已经落地的格子不会再被后面几份挑中，
   所以一批 4+4 份就是 4+4 只，**不会自己撞自己**（否则随机交错时后面产出的元素会落到前面刚产出的
   那一格上就地反应掉，表现成「说好各 4 份，最后只数出 4 份」）。预约在每次「产生」开头清空。
1. **优先撞已有元素**：范围内第一个被元素占着的格子（行优先；不含复合元素占的格子、不含已预约的格子）。
   撞上去就按图2 的表结算 —— 相克：输家消失；相生：输家就地变。
   **同元素**（只可能是「范围内原有的同种元素」，因为自撞已被预约挡住）：这一份换到范围内的另一个空格
2. 范围内没有被占的格子 → 取**离中心最近**的空格（排序：曼哈顿距离升序 → 同行按 x 升序）
3. 全都没有 → 记一次出生失败，这一份浪费掉（**绝不越出范围**）

产出份数的三个计数（`GameEngine` 上）：

| 属性 | 含义 |
|---|---|
| `CompositeProducedCount` | **尝试**产出的份数（= 落地的 + 被挡的）。想验证「默认 4+4」用这个 |
| `CompositeProducedSpawns` | 其中**真的在空格上生成了一只新元素**的份数（撞在已有元素上反应掉的不算） |
| `CompositeProducedEncounters` | 产出撞上已有元素、发生反应次数 |

⚠ **复合元素占着的格子既不参与反应、也不能被覆盖**：取格时直接跳过。
两个复合元素相邻时这一点尤其要紧 —— 否则「同元素换格」会把元素放到隔壁复合元素那一格上，
`Board.Put` 直接抛异常（这个崩溃修过一次，现在有 `相邻复合元素_*` 三条用例钉着，见第十节）。

> 「两个复合元素相邻，生成元素会不会反应？」——分两半：
> **不会**和复合元素本身反应（它是惰性的、不参与任何反应），
> 但会**和另一个复合元素刚产出的元素**正常反应（照旧走图2 的表）。
> 而且两个复合元素是**各自一步**依次产生的（按 uid 顺序），所以不存在「同时生成、谁先谁后说不清」。

#### 产出顺序：默认随机交错

`Rules.CompositeRandomProductionOrder`（**默认开**）：

- **开**：两种组成元素铺成「成对交错」的底（A,B,A,B…），再用**引擎自己的随机源**做 Fisher-Yates 整体打乱。
  不会再出现「先把木铺满最近的一圈、再铺火」这种一坨一坨的形态。
- **关**：按配方顺序「A 的 N 份产完再产 B 的 N 份」—— 图2 表格那句「生产：木+4、火+4」的字面读法。

⚠ 这是**可复现的「随机」**：用的是 `GameEngine` 的随机源（同种子逐位复现，测试里也能用
`SetNextRandomValues` 完全接管），不是 `System.Random` 那种不可控的东西。
步骤记录里那条说明会标注「（两种随机交错产出）」，调试时一眼看得出当前模式。

### 开不开：总开关 `UseCompositeElements`

- **不勾**（默认）= 这一关**完全没有**复合元素，也没有秘术牌：
  抽不到融合 / 分解牌、场上不会出现复合元素、`initialComposites` 会被忽略、
  牌用不出去时提示直接指向这个开关。行为与加这层玩法之前**逐位一致**。
- **勾上** = 这一关玩这一层。面板上勾开关时会**顺手把秘术牌填成「两个都要」**（这是你能勾到的最小操作），
  默认配比是元素 10 / 融合 10 / 分解 5，之后再按需要细调。

> 旧关卡资产反序列化出来是「不勾」，所以不需要任何兼容代码；反过来也意味着
> **给老关卡加这一层玩法必须显式勾上开关**。配了秘术牌或初始复合元素却忘了勾的话，
> 配置校验会明确报出来，不会静默失效。

### 比例可控：秘术牌怎么进牌堆

勾上总开关之后，抽牌按**权重**抽：先决定「这一张是元素牌还是哪种秘术牌」，再决定具体内容。
三个权重都在 `Rules` 上，关卡作者直接填：

| 字段 | 默认 | 含义 |
|---|---|---|
| `UseCompositeElements` | `false` | **总开关**：这一关有没有复合元素与秘术牌 |
| `SpecialCardPool` | `None` | 本关**能抽到**哪些秘术牌（融合 / 分解 / 两个都要）。面板上勾总开关时会自动填成「两个都要」 |
| `ElementCardWeight` | 10 | 元素牌的权重 |
| `FusionCardWeight` | 10 | 融合牌的权重 |
| `DecomposeCardWeight` | 5 | 分解牌的权重 |

例：元素 10 / 融合 10 → 手牌里大约一半是融合牌；把融合牌权重调到 0 就等于关掉它；
只想给融合牌不想给分解牌，就在 `SpecialCardPool` 里把分解牌取消勾选。

有两张死牌会被**自动跳过**（抽不到，也就不会污染手牌）：

- 元素池里凑不出任何一对配方（比如本关只有金一种元素）→ **融合牌**跳过
- 这一关根本不可能出现复合元素（既没初始复合元素、又合不出来）→ **分解牌**跳过

### 关卡里怎么配

- **`Rules.UseCompositeElements`：这一关玩不玩复合元素**（Inspector 上一个勾选框）
- `Rules.SpecialCardPool` + 三个权重：玩的话给哪几张秘术牌、比例多少
- `Rules.InitialComposites`（`LevelDefinition.initialComposites`）：**开局就摆几个复合元素**。
  留空 = 开局没有复合元素 → 只能靠融合牌现场合一个（这正是玩法要求的起点）
- `Rules.CompositeRange` / `CompositeIngredientsPerRound` / `FusionRequiresAdjacency` /
  `CompositeProducesOnCreation` / `DecomposeGrantsElementCards`：这一套的其余数值
- 配置校验会报出这些：
  - **忘了勾总开关**，却配了秘术牌或初始复合元素（表现是「全都填好了但游戏里什么都不出现」）
  - 勾了总开关，但秘术牌一张没选、开局也没摆复合元素（这个开关等于白勾）
  - 开了融合牌却凑不出配方、开了分解牌却拿不到复合元素、权重为 0（等于关掉）
  - 初始复合元素坐标越界 / 摆在墙上 / 和元素抢格子
- 关卡资产面板顶部那行摘要会直接写 **`复合元素 开（融合牌、分解牌、权重 10/10/5、开局 2 个）`**
  或 **`复合元素 关`**，不用往下翻就知道这一关到底有没有这一层
- 编辑器里 **TapGJ ▸ 规则与批量模拟** 的「批量模拟」页有同一个总开关
  （没勾时下面整块置灰并说明原因），跑批报告里会多打一行
  「融合 N 次 / 分解 N 次 / 复合元素产出 N 个 / 场上最多同时 N 个」

### 第二章 5 关现在是怎么配的

> 这一章的教学顺序：**合出来 → 收不住 → 拆掉 → 用复合元素当压力源 → 收尾**
> 全部 `Goal = Custom`、`BottleMode = Disabled`、`useEvents = 0`。

| 关卡 | 名字 | 胜利条件（关卡预制体上的组件） | 关键差异 |
|---|---|---|---|
| `ch2_01` | 合成 | `FusionCount(1)` + `ElementKinds(2)`（AND） | 开局没有复合元素，棋盘上摆着金/水/木三种；要先清掉一种再合 |
| `ch2_02` | 分解 | `DecomposeCount(1)` | 开局一个灵泉；**`SpecialCardUnlockRound = 2`** → 第 1 回合只发元素牌，让玩家看着它吐元素 |
| `ch2_03` | 分解五种 | `DecomposeCount(5)` + `requireNoComposites` | **开局一个复合元素都没有**：玩家自己融合、自己拆，来回 5 次 |
| `ch2_04` | 只剩木 | `OnlyTheseElements(木)` | 灵泉当压力源：每回合往场上吐木 + 水，玩家只能用木牌把水一个个转成木 |
| `ch2_05` | 收尾 | `FusionCount(1)` + `EqualElementCounts(±1)`（AND） | 金比别的多 2 个，先砍掉一个再合，合完数量刚好平 |

几条踩过的坑（数值别照抄，照**原因**改）：

- `ch2_02` / `ch2_03` 的**抽牌只发生在每回合准备阶段之后**：手牌满了就一张都不抽。
  所以 `ch2_02` 第 1 回合玩家得把元素牌打出去，第 2 回合才有位置接分解牌；
  `HandLimit` 太小时手牌会被一种牌堵死（测试脚本里就撞见过「6 张融合牌、场上还有一个拆不掉的复合元素」）。
  `ch2_03` 因此把 `HandLimit` 提到 6、权重调成 元素 30 / 融合 30 / 分解 18。
- **空格召唤：20 关全开**（章节 1 教过的基础操作，逐关关掉会让人以为功能丢了；`Chapter4Tests` 有一条用例钉住）。`ch2_03` 更是必须开：融合要求两个元素十字相邻，
  开局那 5 个孤零零的元素根本凑不出一对，不给召唤就无从下手。
- `ch2_03` 关掉了 `CompositeProducesOnCreation`：融合当回合就产 4 个元素，会把「合一个→拆一个」的循环搅乱，
  「复合元素会不断产元素」这件事让 `ch2_02` / `ch2_04` 去演示。
- `ch2_01` / `ch2_05` 也不能开 `CompositeProducesOnCreation`：多出来的元素会当场破坏「恰好两种」/「数量平均」。

### 第三章 5 关：小瓶子教学

> `ch3_02`~`ch3_05` 的目标是 `BottleProducedRule`（「某元素的瓶子这局一共产出过多少张牌」）；
> `ch3_01` 用的是**内置目标**「水元素 ≤ 0」。全部 `useEvents = 0`、**空格召唤全开**、
> **牌池 = 元素池 = 全部五种**（只有 `ch1_01` / `ch1_02` 两个纯教学关保留单一种牌）。
> 从 `ch3_02` 起还**沿用第二章的复合元素/秘术牌**（叠加，见下面的「机制叠加」）：
> 秘术牌权重压到元素牌的 1/10（10/1/1）、手牌上限 +1 到 6，回合上限与目标张数一律不动。

| 关卡 | 名字 | 目标 | 瓶容量 | 回合上限 | 场上 | 牌池 |
|---|---|---|---|---|---|---|
| `ch3_01` | 喂瓶 | 水 = 0（把水清光） | **5** | 6 | 水 5 / 火 6 | **只有土牌**（教学） |
| `ch3_02` | 攒满一瓶 | 火瓶 1 张 | **5** | 12 | 火 26 | 五种全开 |
| `ch3_03` | 金牌与木牌 | 金瓶 1 + 木瓶 1 | **5** | 12 | 金 10 / 木 10 / 土 5 | 五种全开 |
| `ch3_04` | 三色瓶子 | 水瓶 1 + 土瓶 1 + 火瓶 1 | **5** | 12 | 土 6 / 水 7 / 火 5（起手固定 4 木 1 土） | 五种全开 |
| `ch3_05` | 五行一圈 | 五种各 1 张 | **5** | 12 | 金木水火土 各 5（起手 5 张火） | 五种全开 |

> **`ch3_01` 是这一节的「第一课」，所以故意用固定牌池**：牌池只有土牌 → 起手必定 5 张土牌，
> 而场上正好 5 只水 → **一回合就能清完**。这一回合里玩家会看到：杀水 → 瓶子一格一格涨 →
> 第 5 个水消失时「瓶满，获得 1 张水牌」→ 立刻结算。教学点全在这 5 次出牌里，不需要运气。
> 这和第一章的 `ch1_01`（只有金牌）/ `ch1_02`（只有水牌）是同一个套路：
> **每一节的第一课都保留单一牌池**，后面才放开。

> **瓶子容量全游戏统一 5 格**（20 关都是 5；只有事件「玉翁舒展」会把某一回合临时改成 7、
> 「玉翁敛息」临时改成 3）。所以「1 张瓶牌 = 该元素消失 5 次」——
> 一局某种元素牌只抽得到约「出牌数 ÷ 5」张（12 回合 × 5 = 60 次出牌 → 每种约 12 张），
> 这就是 `ch3_02`~`ch3_05` 的目标都压到「各 1 张」的原因。

> **`ch3_01` 为什么不用「只剩火」**：换成「水 = 0」—— 教的东西一模一样（杀水 → 喂水瓶），
> 但玩家召唤什么、相生什么都不会把自己锁死（「只剩火」时，一旦场上出现清不掉的土就无解）。

**教学脉络是一条相克链**：火克金 → 金克木 → 木克土 → 土克水 → 水克火，
每杀一种元素，它的瓶子就给你**被杀的**那种元素的牌 —— 也就是说**瓶子是下一环的弹药库**：

```
ch3_01  「杀 → 瓶涨 → 满 5 给一张牌」：攒的过程看得见（5 个水 → 1 张水牌）
ch3_02  数量目标：容量 5、要 1 张 → 让 5 个火消失（火给够 26 个）
ch3_03  接力：火牌烧金 → 金瓶给你金牌 → 金牌砍木
ch3_04  链条再长一环：木→土→水→火
ch3_05  五行一圈：火→金→木→土→水→火
```

**张数是怎么定的**：出牌预算是硬的 —— 一局最多打出「回合上限 × 手牌上限」张牌，
而**「产 N 张牌」= 该元素消失「5 × N」次**，每次消失基本要一张**指定元素**的牌
（相克：杀火要水牌、杀金要火牌…）。牌池五种全开时，某种牌一局大约只抽得到「出牌数 ÷ 5」张：

| 关卡 | 需要几张指定元素的牌 | 结论 |
|---|---|---|
| `ch3_01` | 不按张数算（目标是「水 = 0」） | 5 个水、6 回合 ✅ |
| `ch3_02` | 5 张水牌（1 张 × 容量 5） | 12 回合 ✅ |
| `ch3_03` | 5 张火牌（烧金）；木牌由金瓶自供 | 12 回合 ✅ |
| `ch3_04` | 5 张木牌起手 → 后面全靠链条自供 | 12 回合 ✅ |
| `ch3_05` | 5 张火牌起手 → 后面全靠链条自供 | 12 回合 ✅ |

> 这张表用一份**出牌经济模拟**（只算抽牌/打牌/弃牌/瓶产出，不含棋盘细节，每关 400 个种子）验过：
> 上面这套配置通关率 **100%**；而如果保留更大的张数（例如容量 5 + 火瓶 3 张 = 15 次消失）
> 通关率只有 ~50%，必须靠加回合数或收窄牌池才救得回来。

**这一章的两个陷阱（都是设计意图，不是 bug）**：

- **相生不喂瓶**：把水牌打在木上（水生木）只会让木「换身份」，瓶子一点都不涨。想喂瓶只能靠相克。
- **瓶子给的牌杀不了同族**：杀火拿到的是火牌，而火牌点不了火（同元素不出反应）——
  这些牌要么去杀别的元素，要么在弃牌阶段丢掉（不然下回合抽不到新牌）。
- ⚠ `ch3_05` 的场上元素数量**刚好等于**目标所需（五种各 5 个、各要消失 5 次），
  手滑用相生把某种元素转掉就再也补不回来（只能重开）。想让它们宽容一点，就把场上各元素多加 1~2 个。
- **局内怎么看瓶子**：uGUI 局内界面**没有**瓶子条（只有旧的 IMGUI `Hud` 画），所以第三章靠两处顶：
  目标进度条写成「火牌 0 / 1（瓶 3/5）」（括号里是当前这一格攒了几个），
  以及每次喂瓶时提示行会闪一句「金瓶 +1」/「金瓶子满，获得 1 张金牌」。
  要真正的瓶子条得在 `BattleGameplay.prefab` 里加 5 个进度条再接 `engine.Bottle`。

### 第四章 5 关：事件牌

> 本章开始「棋盘不再完全由你控制」：每隔几回合会从事件池里抽一条，只作用于当回合。
> 目标仍然全在关卡预制体上，`useEvents = 1`，事件间隔都调到 **2~3**（第 5 关是 1~2），
> 所以第一波事件最晚第 4 回合就会来 —— 配置校验会检查「回合上限够不够撞上第一次事件」。

| 关卡 | 名字 | 目标 | 事件池 | 这一关在教什么 |
|---|---|---|---|---|
| `ch4_01` | 发牌事件 | 分解 2 次且不剩复合元素 | 元素馈赠、秘术馈赠 | 开局摆着烬 + 熔岩两种复合元素，分解牌权重只有 2 —— **牌主要靠事件发** |
| `ch4_02` | 固定范围事件 | 五个瓶子各 1 张 | 火流漫溢（固定）、土流漫溢（固定） | 右下角那片 **3×3 每次都在同一位置**被改写：固定的区域要提前让开 |
| `ch4_03` | 随机范围事件 | 只剩土 | 水流漫溢、火流漫溢（随机 3×3） | 清完又被糊一层，**而且每次位置都不一样** |
| `ch4_04` | 只剩金和土 | 只剩金、土 | 元素馈赠、木流漫溢（散落 9 格） | 事件不停撒木；金克木、土克水、水克火，别手滑把金或土也砍了 |
| `ch4_05` | 平均元素 | 数量平均 ±1（五种都在场） | 元素馈赠、金流漫溢、静滞结界 | 收尾：开局金 6 比别的多 4，五个瓶子 + 秘术牌都在，边补边砍 |

几条设计上的取舍：

- **`ch4_01` 的分解牌权重只有 2**：这一关就是要「等事件发牌」。全设成 0 会让配置校验报
  「开了分解牌但权重是 0 = 等于关掉」，所以留一个很小的保底值 —— 手气好能提前拆，运气差就得等事件。
  它同时开了 `AllowMultipleComposites`（开局就有两个复合元素，不开的话校验会提醒「融合牌用不出去」）。
- **`ch4_02` 的固定矩形 = 右下 3×3**（`rectX 5, rectY 3, 3×3`）：20 个「要杀的元素」全摆在这块外面，
  否则它们会被就地转换掉（转换**不喂瓶**，等于白摆）。
- **事件的随机性会让每次开局都不一样**，所以这些关的离线验证是「20 个种子跑一遍」而不是单局数字。
- 事件给的元素牌**允许顶破手牌上限**，所以这四关的弃牌阶段是真的要用的（不弃就抽不到新牌）。

### 机制叠加：后一章不再关掉前一章

> 这一版的地板规则是**加法**：新章节只加新机制，不在下一章把它删掉。
> 机制本身仍然是**逐关开关**（`Rules.BottleMode` / `UseCompositeElements` / `useEvents`），
> 章节配置不管玩法 ——「叠加」落在每一关的数值上，不是代码里的继承。

| 章节 | 本章新机制 | 沿用的旧机制 |
|---|---|---|
| 第一章 | 相克 / 相生 / 空格召唤 | — |
| 第二章 | 复合元素 + 秘术牌（融合 / 分解） | 空格召唤 |
| 第三章 | 小瓶子 | 空格召唤 + 复合元素/秘术牌（`ch3_02`~`ch3_05`） |
| 第四章 | 回合事件 | 空格召唤 + 小瓶子（五关）+ 复合元素/秘术牌（`ch4_01`、`ch4_03`~`ch4_05`） |

四条硬规矩（改配置前先看）：

- **`ch3_01` 是唯一例外**：它的教学前提是「牌池只有土牌、起手 5 张土牌」，
  所以它保持纯瓶子教学、不开秘术牌（`Chapter3Tests` 钉着）。
- **秘术牌在第三章只是点缀**：`ch3_02`~`ch3_05` 的权重是 元素 10 / 融合 1 / 分解 1，
  手牌上限 5 → 6 吸收稀释；**回合上限（12）和目标张数一律不动**。
- **第四章的复合元素不产元素**：`ch4_03`~`ch4_05` 的目标看的是「场上只剩 X / 数量平均」，
  复合元素每回合吐元素会把目标一直搅乱，所以 `CompositeProducesOnCreation = 0`。
- **`ch4_02` 不叠秘术牌**：它的目标就是「五个瓶子各产 1 张」，牌堆里只留元素牌最干净。

> 对应的断言：`Chapter3Tests.第三章从第二关起沿用第二章的秘术牌_第一关仍只教瓶子`、
> `Chapter4Tests.第四章五关都保留小瓶子_后三关再叠上秘术牌`。改哪一关的开关，这两条会直接报出来。

### 几个实现上的取舍（想改的话从这里下手）

- **复合元素和元素小怪都用同一个表现对象**（`Creep_{uid}`）：复合元素多一层光环、用专用配色。
  这样 `BoardView.Sync()` 的「多退少补」对账语义一行都不用改，不变量也还是
  「表现对象数 = 元素数 + 复合元素数」
- **`Board.At(pos)` 只返回元素小怪**，复合元素那格返回 `null`；
  要拿占格者一律用 `Board.OccupantAt(pos)`，「这格空不空」一律用 `Board.IsEmpty(pos)`。
  ⚠ 这里踩过一个真实的坑：移动判定原来写的是 `At(next) == null` 就当空格，
  于是小怪会**直接走进复合元素那一格**，然后在 `Put` 里抛异常。修法是改判 `!IsEmpty(next)`，
  并且加了「复合元素挡住的移动要记一条 Bump」的用例（`CompositeElementTests`）
- **融合的两个素材不喂小瓶子**（消耗 ≠ 湮灭），分解也不喂 —— 所以 `RemoveCreep` 多了一个
  `feedBottle` 参数
- 但融合的素材**会**计入 `TotalRemoved` / `RemovedCounts`（它们确实从棋盘上消失了），
  这一点和「瓶子只认相克」是两回事，别混

## 九、回合事件（每隔几回合来一次的扰动）

「事件」是**本局随机、只作用于当回合**的扰动。它和「关卡机制」分工明确：

| 想改什么 | 用什么 | 谁写 |
|---|---|---|
| 这一关**固定**的规则（每局都一样） | `ILevelRule` 组件（挂关卡预制体，见第五节） | 写代码的人 |
| 这一局**随机**的扰动（每局不同） | `IRoundEvent` 资产（本节） | 配资产；只有加**新效果类型**才写代码 |

### 触发规则

- **第 1 回合不触发**，之后每隔 `Rules.EventIntervalMin ~ EventIntervalMax` 回合（默认 **3~6**）触发一条
- 第一次落在 `1 + [min,max]` 回合（默认第 **4~7** 回合）；每次触发后**重新随机**间隔
- 间隔 **每关可调** —— 6 回合的短关卡建议在 `Rules` 里写 `2~3`（否则一局都碰不上，校验会报出来）
- **不放回**：同一局里一条事件最多出现一次；池子抽空后**重洗**（不会「后面几回合没事件」）
- **均匀概率**：不做权重（真要调平衡时再加）
- 触发点：`BeginRound()` 里、**关卡机制的 `OnRoundStart` 之前**、小怪移动之前
  → 所以「静滞结界」真能定住本回合所有小怪（包括机制刚生成的那些）

### 为什么调度在 Core 里，而且用独立随机流

「第几回合来、来哪条」由引擎决定（否则测试与「同种子复现」都谈不上），而且用的是
**从 `Seed` 派生出来的独立随机流**（`GameEngine.EventStreamSeed`），不是玩法那条 `_rng`：

> 如果用共用的 `_rng`，玩家多打一张牌（出生格要随机）就会把后面的事件时间表整个挤歪，
> HUD 上那句「下一次：第 8 回合」立刻变成谎话。独立流保证**同种子 = 同一套事件时间表**，
> 与玩家怎么打无关 —— 预告和复现都靠它。

### 每条事件的边界（都是刻意定的）

- **元素馈赠**：允许手牌超过 `HandLimit`（和「瓶子满自动产牌」同一个口径）。
  副作用是**弃牌阶段终于有事可做** —— 第一节记的那个「弃牌阶段空转」问题被这条事件激活了。
- **秘术馈赠**：引擎里「秘术牌能不能打出去」由 `Rules.HasSpecialCard(kind)` 决定，
  所以在只开了融合牌的关卡里白送分解牌 = 一张死牌 → 这条事件**只在融合+分解都启用时适用**
  （`IsApplicable` 挡住；配错的话关卡校验会直接报）。
- **玉翁敛息**：先结账再降容（4/3 → 1 张牌 + 余 1），观感是「葫芦把憋着的气吐出来」，
  而不是「上限变了但什么也没发生」。本关容量本来就等于目标值时它等于没做事 → 当成「不适用」跳过。
- **静滞结界**：实现就是「准备阶段直接跳过移动」—— 不走 = 不会相遇 = 不会相生/相克。
  比「照常走但相遇不结算」干净（后者还要重新定义「异元素相遇算不算挡路」）。
  **复合元素的每回合产出照旧**（它是产出元素，不是元素之间的相互作用）；玩家出牌照样能引发反应。
- **流漫溢**：**最多凭空 +9 个元素**，是这套里最强的一条。目标元素不在本关 `ElementPool` 里时
  整条**不适用** —— 否则会打破「棋盘上永远只出现池内元素」那条硬不变量（那条不变量一条测试都没改）。

### 生命周期

```
BeginRound
  ├─ 回合数 +1、本回合状态清零（含 SuppressCreepMovement = false）
  ├─ 轮到事件 → 抽一条 → IsApplicable 不适用就换下一条（不算抽过）→ Apply
  ├─ 关卡机制 OnRoundStart
  └─ 准备阶段推进（复合元素产出 → 小怪移动 / 或被静滞定住）
抽牌 → 玩家行动 → 弃牌
判定阶段
  └─ RevertRoundEvents()：撤销临时效果（瓶子容量改回 Rules.BottleCapacity），再判胜负
```

一次事件产生的所有变化**排成一个 `StepRecord`**（`IsRoundEvent = true`，第一条事件的类型是
`GameEventType.RoundEvent`），所以表现层会照常按顺序播，不会「先炸后动」。

### 事件能改什么（注入 API）

| API | 作用 |
|---|---|
| `engine.GiveElementCards(n)` | 从牌池均匀给 n 张元素牌（允许超上限） |
| `engine.GiveSpecialCards(n)` | 每种**本关启用**的秘术牌各给 n 张 |
| `engine.ApplyBottleCapacity(c)` / `RestoreBottleCapacity()` | 本回合改瓶子容量（前者先结账）/ 改回本关的值 |
| `engine.SetSuppressCreepMovement(bool)` | 本回合小怪不移动 |
| `engine.ConvertCellsToElement(element, n)` | 随机散落 n 格 → 该元素（空则添加、有则就地转换） |

容量事件与算盘共用充能和发牌流程：兑换时记录真实手牌 ID、当前门槛和余数，飞牌结束后显示新牌；判定阶段恢复门槛也会同步算盘，但不会再次发牌。

⚠ 这几条**都不喂小瓶子**（转换 / 生成不是「元素消失」），也都不绕过 `ElementPool` 硬约束。

### 写一条新事件

```csharp
[CreateAssetMenu(fileName = "Event_某某", menuName = "TapGJ/事件/某某")]
public sealed class Event_MyThing : RoundEventDefinition
{
    [SerializeField, Min(1)] int count = 2;

    public override bool IsApplicable(GameEngine engine, out string reason)
    {
        if (engine.Rules.PoolCards.Length > 0) { reason = null; return true; }
        reason = "本关牌池里一张元素牌都没有";
        return false;
    }

    public override void Apply(GameEngine engine) => engine.GiveElementCards(count);
}
```

- 想做**同一条事件的变体**（给 5 张木牌、转 9 格火）= 复制资产改参数，**不用写代码**
- 想加**新的效果类型**才写类：继承 `RoundEventDefinition`，实现 `Apply`；需要撤销就再实现 `Revert`
- 加完记得把它拖进 `EventCatalog`（只是清单，不影响运行），再放进要用它的关卡的 `roundEvents`

### 关卡校验会报什么

`LevelDefinition.CollectAuthoringIssues` 里多了一块（Inspector 实时刷新、「校验所有关卡」、进关时三处共用）：

- 勾了 `useEvents` 但 `roundEvents` 是空的（白勾）
- 配了 `roundEvents` 但没勾 `useEvents`（永远不会触发）
- 事件池里有空槽位 / 同一条事件放了两次（去重按 `Id`，重了等于只有一条）
- **回合上限撞不上第一次事件**（`1 + EventIntervalMin > RoundLimit` → 永远不会有事件；
  `1 + EventIntervalMax > RoundLimit` → 有些局可能一个都碰不到）
- **某条事件在本关不适用**（目标元素是池外的 / 没开复合元素 / 本关容量本来就一样 …）

「适不适用」问的是事件自己的 `IsApplicable` —— 运行期抽取用的是同一个方法，
所以 Inspector 里报的「会被跳过」和 Play 时跳过的**必然是同一批**。
（为了让它判断得准，校验时会真的**在内存里开一局**：不然「场上一个小怪都没有」这类判断在空棋盘上永远成立。）

另外菜单 **TapGJ ▸ 校验所有事件（目录 + 全部事件资产）** 单独扫一遍所有事件资产：
Id 重复、没填说明、目录里有空槽位。

### HUD

- 右侧面板多了 **「本回合事件：<名字>：<说明>　下一次：第 N 回合」**（本关没开事件时整块不显示）
- 触发时日志里有一条 `—— 回合事件：静滞结界 —— 本回合元素不会自主相互作用`
- 瓶子进度条读的是 `Engine.Bottle.Capacity`（**本回合实际生效的容量**），不是 `Rules.BottleCapacity`（基准值）——
  事件改容量时只有前者会变，读错就会显示 4/5 而实际 3 就爆

    「元素池里有没有可配对的组合」这条判断（只有金 → 没有配方）

    - 后产生的那个会**撞上前一个刚产出的元素**并按图2 的表反应

    配不上的两种元素合不了（并给出配方）、**场上已有复合元素时用不出去**、
    关掉 `FusionRequiresAdjacency` 之后远处的元素也能合、

## 十一、已知限制

### 内容 / 玩法

- **元素自己会走（`Rules.MaxMoveSteps`，默认 3 = 每回合走 0~3 格）** —— 这是图1 准备阶段的核心规则。
  早期做章节关卡时我把它全设成了 **0**（为了让固定布局的谜题可复现、也方便离线验证），
  结果整局变成静止棋盘：元素永远不动、不会自己相生相克，玩起来像「功能丢了」。
  **现在 20 关全部恢复成 3**，并在 `Chapter4Tests` 里钉了一条「所有正式关卡的元素都会自己移动」。
  > ⚠ 第二~四章的数值都是按**静止棋盘**调的，恢复移动后需要逐关复验：
  > · 会变简单的：瓶子类关卡（元素自己撞死的也算「消失」，白喂瓶）、
  >   「只剩某元素」类（自己相克就清掉了）；
  > · 最可能被破坏的是 `ch3_05`（场上五种各 5 个，正好等于目标）—— 元素自己互撞就可能把五个瓶子
  >   一起喂满，那一关的「自己走出相克链」的乐趣会被系统代劳。真要保谜题感，给这一关单独设
  >   `MaxMoveSteps = 0`（或把目标张数调高），并在关卡描述里说明。

- **牌池策略：三个「第一课」保留单一种牌，其余全部五种全开**。
  `ch1_01`（教相克，只有金）、`ch1_02`（教相生，只有水）、`ch3_01`（教小瓶子，只有土）——
  这三关就是要让玩家专注一种牌、**一回合把一件事做完**；其余关卡
  `ElementPool = CardPool = 全部五种`。单一牌池的代价是测试反馈过的：
  **每张牌都一样（没有决策空间）**，而且玩家一旦偏离预期路线就没牌可用、直接卡死 ——
  所以只在「第一课」上用。`Chapter4Tests` 里有一条用例钉住这个约定。
  > ⚠ 牌池开宽后，「产 N 张某元素牌」这类目标要按 **出牌预算 ÷ 5** 重算
  > （一局 8 回合 × 5 张 = 40 次出牌，某种牌大约只抽得到 8 张）—— 第三章那张换算表就是干这个的。

- **元素牌打在空格上 = 召唤（图1 第 2 条）在所有关卡固定开启**，旧配置中的拒绝开关不再生效。
  **这条规则会让「某元素 ≥ N / 只剩水」更容易、
  「清空 / 某元素 ≤ N」更麻烦** —— 数值上先人工试玩再定
- **批量模拟覆盖不到召唤**：`GreedyPlayer` 不会主动召唤（凭空多一只元素对它的目标没好处），
  所以第四节那些胜率数字和「召唤好不好玩」无关，`规则与批量模拟` 的汇总里会明确写出这一点
- 召唤**没有机制版注入 API**（机制要往空格放元素用 `SpawnAt`）。两者不是一回事：
  `SpawnAt` 计入 `SpawnedCounts`、召唤计入 `SummonedCounts`，而且召唤不通知任何关卡机制
- **复合元素与秘术牌默认是关的**：`Rules.UseCompositeElements` 默认 `false`（总开关不勾就完全不影响老玩法）。
  要让某一关玩这一套，**用关卡面板上的「启用复合元素（用默认配比）」按钮**（它会顺手把秘术牌填成两张都要），
  或者自己把 `rules.UseCompositeElements` 和 `rules.SpecialCardPool` 两个字段都填上。
  ⚠ **运行时不会替你自动补**牌池 —— 只勾总开关、池子留空是「这一关有复合元素但一张秘术牌都不发」
  （配置校验会报「这个开关白勾」）。**第三章 `ch3_02` 起、第四章 `ch4_01` / `ch4_03`~`05` 是显式开的**，
  见第八节「机制叠加」
- **秘术牌只能靠抽牌拿到**：满瓶产出的牌永远是元素牌；现在也没有「机制发一张秘术牌」的现成组件
  （要的话调 `engine.DrawSpecialCard(CardKind)` 就行，沙盒/机制都能用）
- **分解牌不占每回合出牌上限**（它是纯解场牌）。想让它也吃上限，把 `TryPlayDecomposeCard` 里
  `CheckSpecialCardPlayable` 的那一段复用过来即可
- **复合元素每回合都会「产生」满额元素**，`CompositeIngredientsPerRound = 4` 时两种元素各 4 个，
  一个复合元素就是每回合 +8 只 —— 数值上很可能偏强，先用第八节的模拟器跑一遍再定
- **复合元素不计入任何胜利条件**（它既不算元素、也不进元素种类统计）。
  所以「全场只剩水元素」之类的目标在有复合元素的关卡里是按**元素**判的，不看复合元素
- 玩家没有出牌次数限制（原型故意放开，方便试；调参数据见第四节，4 张较平衡）
- **`Assets/Levels/` 里还没有关卡资产**：`LevelCatalog.asset` 与 `Level_NN` 都还没建，
  所以现在 Play 走的是 `GameSession` 上的「开发兜底规则」随机铺盘。先跑一次 **TapGJ ▸ 新建关卡**。
  另外「开发兜底规则」这一份的总开关也是关的 —— 想手玩秘术牌，在 `GameSession` 的
  Inspector 上把兜底 `Rules` 的 `UseCompositeElements` 勾上即可（它会自动展开出下面那一组设置）
- 墙格在关卡初始布置（P2）和运行中（P3 的 `BlockCell`）都能用；但**墙不会自动围住棋盘**，
  也没有「墙被破坏」的机制，需要的话自己写一个 `LevelRuleBehaviour`
- **复合元素的操作入口只有秘术牌**：没有「用机制在某个格子生成复合元素」的注入 API
  （`GameEngine.PlaceComposite` 是沙盒/测试用的，不计入步骤队列）。
  要加机制版的话照 `SpawnAt` 写一个 `SpawnCompositeAt` 即可
- 关卡预制体本身还是空壳挂点：机制组件有了，但**内置的美术/关卡逻辑一个都没有**
- 主界面场景还没做：游戏侧已经把接口冻结成 `LevelCatalog` / `SceneFlow` / `ProgressStore` 三个入口

### 回合事件

- **强度完全没校准**，这是最需要试玩的一条：
  - 「元素馈赠 3 张」+「玉翁敛息结账」撞在同一回合 ≈ 白送 **5 张牌**（≈ 多打一个整回合），短关卡里尤其猛；
  - 「流漫溢」最多**凭空 +9 个元素**，对「某元素 ≤ N / 清空全场」这类目标是**灾难**，
    对「某元素 ≥ N」是神助 —— 但它是随机的，玩家没法防。
  数值都在资产参数里（`count` / `cellCount` / `capacity`），改完不用重新编译。
- **转换事件 × 清空类目标** = 纯运气背刺：目标「火 ≤ 0」的关卡抽到「赤焰漫燎」基本就废了。
  现在唯一的对策是**按关裁剪池子**（那一关的 `roundEvents` 里别放它），校验**不会**替你判断这种组合。
- **静滞结界 × 相生计数机制**：那回合进度条白给（不是死局，但玩家会以为卡了）。同样只能靠池子裁剪。
- **事件没有美术表达**：`BoardView.PlayStep` 里**没有** `GameEventType.RoundEvent` 的 case，
  所以触发时只有日志一行 + 面板一行，棋盘上不会弹「事件卡」。要接美术就照第六节那个挂点加 case。
- **事件池不支持权重**（均匀等概率），也**不支持同一回合来两条**（`ActiveEvents` 是列表，但调度只抽一条）。
  加权重的话照 `Rules.DrawWeightOf` 那套写即可。
- **批量跑批 / 平衡探针不含事件**：`BalanceProbeTests` 与 `PlayLimitTuningTests` 都不挂事件池，
  所以第四节那些胜率数字是「没有事件」的世界。要看事件对胜率的影响，得先给跑批加一个开关再重跑。
- **事件不记档**：没有「事件图鉴」也没有「这局见过哪些事件」，重开就全清零（和关卡进度的口径一致）。
- `EventCatalog` 只是清单：关卡校验**不检查**「关卡池里的事件是否在目录里」，
  所以目录漏收一条事件不会报错（不影响运行，只影响你浏览时的完整感）。

### 表现层 / 美术

- Game 场景默认卡面仍是**程序员美术**（纯色方块 + 文字），卡牌消散已依赖导入的美术资源；
  卡牌已经支持预制体（`HandView.CardPrefab`），格子/小怪的外观还只有代码生成。
  接特效/预制体的挂点与注意事项见第六节「美术与特效的接入口」。
- 复合元素复用的是小怪的显示对象（多一层光环 + 专用配色），**还没有自己的预制体通道**；
  想接美术就照卡牌那条双路模式（`HandView.CardPrefab`）给 `BoardView` 也加一个
- 秘术牌在牌面上只是换字换色（「融合」/「分解」，字形缩到 0.62），**没有专门的牌面美术**
- `Assets/yuansupai/` 与 `Assets/sharder/` 已接入成功出牌、弃牌时的卡牌消散，
  两个目录和目录 `.meta` 仍未提交；远端克隆不能直接取得这些资源。
- 相生的表现只是「格子闪一下 + 颜色/元素字换成新的」，没有真正的形变动画
- 准备阶段的动画是「逐只小怪依次播放」，节奏由 `GameSession.StepDuration` 控制（`FastForward()` 可跳过）

### UI

- 游戏内 HUD 还是临时 IMGUI 版（[Hud.cs](Assets/Scripts/View/Hud.cs)）。它实现 `IGameHud`，
  做正式 uGUI 之后**删掉这个文件即可**，主控一行都不用改（见第六节「游戏内 UI：IMGUI → uGUI 的替换路径」）。
- `Hud.CountTargets(Card)` 是**死代码**（没有任何调用点），删 HUD 时一起带走。
- `LevelCatalog.menuSceneName` 目前**没有任何代码读它**（Tooltip 写着「SceneFlow.LoadMenu 用」，与现状不符）；

### 工程 / 场景

- **场景必须手工搭**（或用菜单一键搭骨架）：`Assets/Scenes/SampleScene.unity` **已经被删掉了**，
  但 `ProjectSettings/EditorBuildSettings.asset` 里还留着一条指向它的**禁用**条目，可以顺手清掉。
- **`FastForward()` 只加速移动**：`PlayStep` 里只有 `PlayMove` 用了传进来的 `stepDuration`，
  而 `Bump` / `Transform` / `Vanish` / `Spawn` / `SpawnBlocked` 的时长是**硬编码**的
  （0.18 / 0.20 / 0.16 / 0.16 / 0.14 秒），**不看快进标志**。所以快进时反应动画照旧一秒一秒播 ——
  一局下来仍有几十秒跳不掉。修法是把这些时长收敛到一个「按 `InstantPlayback` 归零/缩放」的入口，
  顺便搬进配置资源（接特效时这件事会更要紧，见第六节）。
- 无头跑测试需要连 Unity 许可服务的**命名管道**，受限环境里会直接以 199 退出；
  编辑器（或 Unity Hub 占着 `Temp/UnityLockfile`）时也跑不了，**不要强删那个文件**。
