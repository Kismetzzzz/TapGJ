# TapGJ — 五行元素卡牌对战原型

Unity 2D 原型，用来验证「8×8 棋盘 + 五行元素反应 + 元素牌」这套玩法能不能成立。
本文件记录**规则是怎么定的、哪些地方原表有歧义、怎么玩、怎么跑测试**。

- 工程版本：Unity **2022.3.62f3**（`ProjectSettings/ProjectVersion.txt`）
- 打开方式：Unity Hub 直接打开 `D:\LiquidCat\TapGJ`，按 **Play** 就能玩（场景里不需要摆任何东西）

---

## 一、核心流程（对应图1）

```
游戏开始 → 第 1 回合
  ├─ 准备阶段：小怪随机移动 0~3 格，不同元素相遇即反应，同元素相遇禁止移动（玩家不能操作）
  ├─ 抽牌阶段：自动把手牌补到上限 5 张（本来就满 5 张则一张都不抽），玩家不需要操作
  ├─ 玩家行动阶段：小怪静止，玩家出元素牌，自己决定何时结束
  ├─ 弃牌阶段：可以弃牌（每回合最多 5 张，也可以全部弃完）
  └─ 判定阶段：达成胜利条件 → 游戏结束；回合数达到上限 15 → 失败；否则进入下一回合
```

一回合的推进完全由 `GameEngine` 决定，表现层只负责把 `StepRecord` 播成动画。
逻辑层与 Unity 无关（纯 C#），所以能在 EditMode 测试里几千次跑批。

### 屏幕分区

对应设计稿：**上方中央 = 棋盘网格，下方 = 手牌区，右侧 = HUD 面板**。

| 区域 | 屏幕比例（左上原点） | 内容 |
|---|---|---|
| 棋盘 | x 4%~66%，y 1%~71% | 8×8 网格、元素小怪 |
| 手牌区 | x 4%~66%，y 73%~97% | 每张手牌一个色块，可点 |
| HUD | 右侧约 30% | 阶段按钮、瓶子、胜负进度、反应日志 |

比例写在 `GameRunner.Zones`，改这一处就能整体挪动。

> **棋盘尺寸只由相机决定**：`GameRunner` 按棋盘区域算相机的 `orthographicSize`，
> 然后 `BoardView.LayoutPixels(..., fitToZone: false)` 只做定位、缩放保持 1。
> 早先版本相机缩一次、棋盘又缩一次（双重缩放），格子被放大到糊满屏幕 —— 这个坑已有测试钉住。

### 上手操作

| 阶段 | 操作 |
|---|---|
| 准备阶段 | 自动播放小怪移动，玩家不用操作 |
| 抽牌阶段 | **自动**补牌到 5 张，没有按钮 |
| 玩家行动阶段 | 点**下方手牌区**的牌选中 → 棋盘上**绿色高亮**能打的目标格 → 点格子出牌；点「结束出牌 → 弃牌」结束 |
| 弃牌阶段 | 点下方手牌区的牌即弃掉（每回合最多 5 张）；点「结束弃牌 → 判定」结束 |
| 任意时刻 | 「重开（同种子）」复现同一局；「重开（换种子）」换一局 |

手牌也能从右侧 HUD 面板的列表里点选，两条路等价；选中的牌会同时在两处高亮。

### ⚠ 一个必须知道的设计问题：弃牌阶段现在是空转的

抽牌阶段是「**补到 5 张**」，所以手牌永远不会超过 5 张；而弃牌阶段是「**弃到至多 5 张**」——
两者用的是同一个数字，**手牌永远满足条件，弃牌阶段一次都不会被触发**。

实测（60 局，每回合出牌不设上限）：平均弃牌 **0.00 张/局**。

要让它有意义，得动其中一条：
- 给玩家行动阶段加**每回合出牌张数上限**（推荐，见下面的调参表）
- 或者把「瓶子满自动产出卡牌」改成会突破上限，让手牌真的能超过 5 张

> 好消息是：**瓶子满产的牌确实能把手上限顶破**，那一种情况下弃牌阶段才有事可做。

## 二、反应表怎么定的（对应图2）

图2 是**按「行元素」逐行写的**。本工程把行元素当作**主动撞上去的一方**、列元素当作**被撞上的一方**。

### 统一读法（已与设计者确认）

原表混用两种句式，单看一对会觉得矛盾（「与火相遇，该金元素消失」和「与水牌相遇水元素+1」到底谁赢？）。统一成一条规则后 10 对全部自洽：

> **这条记录点名的那个元素，就是输家。** 另一方留下并 **+1**（在相邻空格生成一个新的自己）。

- 「与 X 相遇 **X+1**」→ 点名的 X **活下来并 +1**，写作这一行的那一方消失
- 「与 X 相遇 **该 X 元素消失**」→ 点名的 X **消失**，写作这一行的那一方留下并 +1
- 同元素相遇 → 不发生任何反应，只禁止这一次移动
- 例：金行「与火相遇，该金元素消失」点名**金** → 金输、火赢；金行「与水牌相遇水元素+1」点名**水** → 水赢、金变为水

### 10 对跨元素组合的全部结果

| 组合 | 赢家（留下并 +1） | 输家（消失） | 原表依据 |
|---|---|---|---|
| 金 × 木 | **金** | 木 | 金行「与木元素相遇，该木元素消失」 |
| 金 × 水 | **水** | 金 | 金行「与水牌相遇水元素+1」 |
| 金 × 火 | **火** | 金 | 金行「与火元素/火牌相遇，该金元素消失」 |
| 金 × 土 | **金** | 土 | 金行「与土牌相遇金元素+1」 |
| 水 × 木 | **木** | 水 | 木行「与水牌相遇木元素+1」 |
| 木 × 火 | **火** | 木 | 木行「与火牌相遇火元素+1」 |
| 木 × 土 | **木** | 土 | 木行「与土元素相遇，该土元素消失」 |
| 水 × 火 | **水** | 火 | 水行「与火元素相遇，该火元素消失」 |
| 水 × 土 | **土** | 水 | 水行「与土元素相遇，该水元素消失」 |
| 火 × 土 | **土** | 火 | 火行「与土牌相遇土元素+1」 |

> 实现只写一处：`ReactionTable` 的构造函数里 10 行 `WinTarget(...)`，每行还带着对应的原文依据。
> 另外注意：**赢家 +1 是在旁边「生成一个新的自己」，不是原地数量叠加** ——
> 所以一次反应的净效果是「输家消失、赢家在相邻空格多出一个」，棋盘的格子占用不会变少。

图2 下半部分的**复合元素**（烬、熔岩、矿晶、寒钢、灵泉）需要「两个元素合成一个复合元素」的机制，属于第二阶段内容，本原型**未实现**。

## 三、元素小瓶子与元素牌

- 五行各有一个小瓶子，**场上每消失 1 个该元素的小怪，对应瓶子 +1**
- 装满（默认上限 **5**）后自动产出一张**对应元素的牌**，瓶子清零
- 玩家初始随机 5 张牌
- 出牌规则（`Rules.CardEffect`，默认 `CardAsVirtualElement`）：
  把打出的牌当成一个「虚拟元素」主动撞上目标格的元素，按上面同一张表结算 ——
  **目标元素消失**，若赢家就是牌面元素，就在旁边生成一个新的牌面元素。
  - 例：水牌打火小怪 → 水赢、火消失 → 生成一个新水
  - 例：木牌打水小怪 → 木赢、水消失 → 生成一个新木
  - 例：水牌打水小怪 → 同元素不反应 → **该次出牌被拒绝**（不消耗手牌）

> 图1 只写了「对小怪使用卡牌，视为发生作用」，没说清牌面元素与目标元素的关系。
> 如果这不是你想要的解释，把 `Rules.CardEffect` 换成 `SameElementOnly`（只能打同元素）或
> `SameElementSpawnOne`（打同元素并原地补一个）即可。

## 四、胜利 / 失败条件

- 失败：**回合数达到回合上限（默认 15）仍未胜利** —— 第 15 回合结束就判负
- 胜利：默认按图1 的原文实现为「**全场只剩水元素**」
- 另提供 `WinCondition.SingleElement`（**全场只剩一种元素**），作为备用目标，在 Inspector 里切换

### 实测：这两个胜利条件可不可达？

用一份固定的贪心策略（`GreedyPlayer`：能打就打最有利于减少元素种类的那张牌）跑 60 局，
15 回合上限，随机种子固定。加了抽牌阶段之后（每回合补满 5 张、出牌不限张数）：

| 胜利条件 | 胜率 | 平均回合 | 平均出牌 | 终局元素种类（平均 / 最好） |
|---|---|---|---|---|
| 只剩一种元素 `SingleElement` | **60 / 60（100%）** | 5.8 | 33.9 张/局 | 0.42 / **0** |
| 只剩水元素 `WaterOnly`（图1 原文） | **51 / 60（85%）** | 6.2 | 29.0 张/局 | 0.85 / **0** |

**两个条件都变成几乎必胜了** —— 因为每回合补满手牌、出牌又不限张数，玩家一回合能打十几张，
平均 6 回合就把棋盘清空。这正是下面「出牌上限」要解决的问题。

### 调参：每回合出牌上限对胜率的影响

`Rules.MaxCardsPerRound`（0 = 不限，默认）。60 局 × 每档，`PlayLimitTuningTests` 会打这张表：

**胜利条件 = 只剩一种元素**

| 出牌上限 | 胜率 | 平均回合 | 平均出牌 | 平均弃牌 | 终局元素种类 |
|---|---|---|---|---|---|
| 不限（默认） | 60/60 | 5.8 | 33.9 | 0.00 | 0.42 |
| 4 张 | 60/60 | 8.7 | 34.5 | 0.00 | 0.45 |
| **3 张** | **59/60** | **11.1** | 33.1 | 0.00 | 0.62 |
| 2 张 | 23/60 | 14.6 | 29.2 | 0.00 | 2.08 |
| 1 张 | 3/60 | 14.8 | 14.8 | 0.60 | 3.45 |

**胜利条件 = 只剩水元素**

| 出牌上限 | 胜率 | 平均回合 | 平均出牌 | 平均弃牌 | 终局元素种类 |
|---|---|---|---|---|---|
| 不限（默认） | 51/60 | 6.2 | 29.0 | 0.00 | 0.85 |
| 4 张 | 53/60 | 7.8 | 28.1 | 0.00 | 0.88 |
| **3 张** | **60/60** | **8.5** | 25.6 | 0.00 | 1.00 |
| 2 张 | 53/60 | 12.2 | 24.3 | 0.00 | 1.12 |
| 1 张 | 9/60 | 14.9 | 14.8 | 0.50 | 3.00 |

**推荐 `MaxCardsPerRound = 3`**：胜率约 98~100%、平均 8~11 回合结束，
正好落在 15 回合上限以内，既不会五六回合草草收场，也不至于打不完。
而且「每回合只能出 3 张、手上有 5 张」逼玩家做取舍，瓶子攒出来的牌也有了意义。

调成 1 张会难到赢不了（3/60、9/60），2 张开始有挑战（约 40~88%），可以按想要的难度取。

> 提醒：贪心策略很笨，人类玩家（会规划几步之后的元素种类）胜率应该更高。
> 这张表是用来**比不同上限之间的相对难度**，不是绝对平衡目标。

## 五、代码结构

```
Assets/
├─ Scripts/
│  ├─ TapGJ.Runtime.asmdef
│  ├─ ElementDefs.cs              五行定义、配色、程序化贴图
│  ├─ Core/                       纯 C#，不引用 UnityEngine
│  │  ├─ Rules.cs                 所有可调数值（棋盘、步数、手牌上限、弃牌/出牌上限、胜利条件…）
│  │  ├─ Board.cs                 网格、小怪、出生格搜索
│  │  ├─ ReactionTable.cs         ★ 图2 的反应表（10 对赢家，每行带原文依据）
│  │  ├─ GameEvents.cs            阶段、事件、步骤记录（逻辑层→表现层的唯一通道）
│  │  ├─ GameEngine.cs            ★ 回合状态机主流程
│  │  ├─ GameEngine.Sandbox.cs    摆盘 / 固定随机 / 统计（测试与编辑器工具用）
│  │  └─ GreedyPlayer.cs          固定的贪心策略，用来量化「有没有可赢路径」
│  └─ View/                       表现层，全部代码生成，无需美术资源与预制体
│     ├─ GameRunner.cs            自启动、回合驱动、动画播放、屏幕分区与相机布局
│     ├─ BoardView.cs             ★ 棋盘：CellView（静态格子）+ CreepView（小怪）+ Sync 对账
│     ├─ HandView.cs              下方手牌区：每张牌一个可点击的 GameObject
│     └─ Hud.cs                   IMGUI 面板：状态、瓶子、按钮、日志
├─ Editor/
│  ├─ RulesInspectorWindow.cs     菜单 TapGJ ▸ 规则与批量模拟（反应表 / 跑批 / 玩法说明）
│  └─ SceneScaffold.cs            菜单 TapGJ ▸ 在场景里创建游戏主控 / 校验当前场景 / 打印对局状态
└─ Tests/EditMode/
   ├─ CoreRulesTests.cs           规则层测试（开局、反应方向、歧义对、瓶子、出牌、胜负、40 局跑批）
   ├─ BoardViewTests.cs           表现层冒烟测试（64 格、同步、相机布局）
   ├─ BalanceProbeTests.cs        平衡性探针（贪心策略 × 60 局 × 两种胜利条件）
   └─ PlayLimitTuningTests.cs     出牌上限调参表（不限/4/3/2/1 张 × 两种胜利条件）
```

设计上故意分成两层：`Core` 里没有一行 `UnityEngine`，所以规则能被高速批量验证；
`View` 只消费 `StepRecord`/`GameEvent`，改玩法不用动渲染代码。

### 表现层的对象所有权（一条踩过坑的规则）

```
BoardView
├─ Cells/   64 × CellView    静态：底板 + 高亮 + 坐标角标 —— 一辈子不动，也不画小怪
└─ Creeps/  N × CreepView   一只小怪恰好一个对象：色块 + 元素字（元素字是它的子物体）
```

- 小怪位置只用**局部坐标**：棋盘被挪动 / 缩放时它自动跟着走，不需要任何「布局后复位」代码
- `BoardView.Sync()` 是唯一入口，以引擎为准**双向对账**：多的销毁、少的补齐、位置归位
- 动画期间按 **uid** 冻结对应小怪，Sync 不许插手（引擎里记的是这一步**结算完**的状态）
- 元素字挂在小怪下面，所以「色块在哪字就在哪」，消失 / 生成的缩放动画也自动联动

之前不是这样的：格子里放一份小怪、`_creepRoot` 下再放一份，两套并存；
而且清理代码是死代码 —— `ShowEmpty()` 先把字段置空，调用方紧接着 `if (字段 != null)` 判断，
永远进不去，于是格子留下一个**没人销毁的色块**。表现就是两个症状：
「格子有颜色但没有元素字」（孤儿对象）和「方块飞出棋盘」（那一半用的是世界坐标，不跟棋盘走）。
现在这两类都被测试钉住了，见第七节。

## 六、在场景里手工搭（三种方式）
工程默认是「代码自己搭」：场景里什么都不放，按 Play 也能玩（运行时自动创建 GameRunner、Board、Main Camera）。
同时它**也支持你把结构摆进场景**，两种用法不冲突 —— 场景里已经有 GameRunner 时，运行时就不会再自动创建。

### 需要的 GameObject 结构

```
GameRunner          ← 必需（也可以让运行时自动创建）
├─ Board            ← 可选子物体（挂 BoardView）
Main Camera         ← 可选（正交相机；位置与大小由 GameRunner 在运行时接管）
```

- **HUD 没有场景对象**：它是 IMGUI，运行时画在 GameRunner 上
- **不要手工往 Board 下面塞格子**：`BoardView` 会在运行时先清空子物体、再生成 64 个格子
- 所有可调参数（棋盘大小、每种元素初始数量、每回合步数、瓶子容量、回合上限、胜利条件、
  出牌方式、随机种子）都在 **GameRunner 组件的 Inspector** 上，改完直接 Play 生效

### 方式 1：用菜单一键搭（推荐）

菜单 **TapGJ ▸ 在场景里创建游戏主控 (GameRunner)**
→ 自动建好 `GameRunner` + `Board` 子物体（缺 Main Camera 也会补上），并选中它。

菜单 **TapGJ ▸ 校验当前场景** → 检查缺什么、有没有摆错位置，把结论打在 Console 和一个弹窗里。

菜单 **TapGJ ▸ 打印当前对局状态（仅 Play 时）** → Play 期间随时把阶段/回合/场上元素/瓶子/手牌打到 Console。

### 方式 2：完全手工

1. Hierarchy 右键 ▸ **Create Empty**，改名 `GameRunner`
2. 选中它 ▸ Inspector ▸ **Add Component** ▸ 搜 `GameRunner` ▸ 添加
3. （可选）右键 `GameRunner` ▸ **Create Empty Child**，改名 `Board`，给它 **Add Component ▸ `BoardView`**
4. （可选）确认场景里有一个 **Main Camera**
5. 选中 `GameRunner`，在 Inspector 里调 `Rules`（棋盘、回合上限、胜利条件…）
6. 按 **Play**

> 第 3 步不做也可以：`GameRunner` 运行时会在自己下面建一个 `Board`。
> 手动放 `Board` 的唯一好处是它出现在 Hierarchy 里、能被选中查看。

### 方式 3：什么都不放

直接按 Play。运行时 `[RuntimeInitializeOnLoadMethod]` 会检查场景里有没有 GameRunner，
没有就自动创建一套。适合快速迭代 —— 改完代码直接 Play，不用管场景状态。

## 七、怎么验证

**A. 跑测试**（Window ▸ General ▸ Test Runner ▸ EditMode ▸ Run All）：当前 **39 项全部通过**，含
- 反应表 10 对赢家逐对钉死 + 双向一致性
- 每种反应方向的碰撞结果（谁消失、谁 +1、生成在哪一格）
- 「每格最多一个元素」这个不变量（40 个种子 × 逐步检查，共约 600 回合）
- 抽牌阶段：补到上限 5 张 / 已满不抽 / 超过上限不会被削掉
- 弃牌阶段：弃牌减手牌、每回合弃牌上限、弃牌阶段不能出牌
- 布局：棋盘落在规划区域里、缩放不会被二次放大、元素字小于格子（不会糊满屏幕）
- 手牌区：手牌对象数跟着逻辑层走、每张牌可点、选中态正确
- **表现层对象所有权的不变量**（详见第五节）：
  - 小怪对象数在整个回合流程里每走一步都等于 `Engine.CreepCount`（移动 / 相遇 / 消失 / 生成全覆盖）
  - 消失的小怪对象必须被**真的销毁**，不能只丢引用（`== null` 走 `UnityEngine.Object` 的重载）
  - 场景里实际存在的 `Creep_*` 对象数必须和 `BoardView` 记录的一致 —— 多出来的就是孤儿对象
  - 格子下面不许出现任何小怪残留（底板 + 高亮之外一律不允许）
  - 挪动 / 缩放棋盘后，小怪仍然与目标格中心重合
- 同种子完全复现、回合上限判负
- 平衡性探针 + 出牌上限调参表（见第四节实测表）

> 这几条不变量做过**变异测试**：把 `Sync()` 的清理改成「只丢引用、不销毁对象」（复刻旧 bug 的形态），
> 需要有测试失败才算有效 —— 第一版测试确实**没抓住**（小怪只移动时 `_stale` 是空的、
> 浸泡用例把三只摆在不同的行导致 12 回合里一次反应都没发生），补强之后才被抓住。
> 所以用例里还留了「这一局必须真的发生过消失和生成」的兜底断言，防止它以后悄悄退化成空测试。

**B. 批量模拟**（菜单 **TapGJ ▸ 规则与批量模拟**）
- 「反应表」页把 25 条规则画成表格，并自动列出结构性观察
- 「批量模拟」页可改数值后一次跑几百局，统计胜率 / 平均回合数 / 终局棋盘形态 —— 用来回答
  「这个胜利条件到底有没有可赢的路径」
