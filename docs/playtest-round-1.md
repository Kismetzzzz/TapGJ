# 第一轮游戏性试验：三关诊断

**目的不是做出好关卡，而是用最小成本问出「到底缺什么卡、什么规则、什么信息」。**

玩法规则一律不改，只用现在已经能做的东西（元素池 / 牌池 / 字符画布局 / 7 种目标 / 机制组件）。
跑完这三关，你手上应该有一份**具体的**待办清单，而不是猜的。

> ⚠ **补充：图1 玩家行动阶段的第 2 条已实现** —— 元素牌现在**也能打在空格上**，在该格召唤 1 个牌面元素的小怪
> （默认开启，属**新增玩法**，不是「改规则」；见 [README 第三节](../README.md)）。
> 它会影响下面三关的观察结果，玩之前先决定用哪一种：
>
> - **Level 01「引水」**：手牌全是水牌时，「点金格」不再是唯一能做的事 —— 也可以往空格里倒水。
>   「第一个动作必然由玩家发起」仍然成立，但要留意玩家**先点金格还是先点空格**：
>   如果先点空格，那这关量的就不是「相生能不能被自己发现」，而是「召唤看起来像不像在做有用的事」。
> - **Level 02「灭火」**：召唤能把水补进空格，追不上的压力会变小 —— 这关想量的是 `MaxCardsPerRound` 的松紧，
>   建议先把 `EmptyCellCard` 选成 **`Reject`**（回到旧玩法）再跑，别让两个变量混在一起。
> - **Level 03「相生计数」**：召唤**不算相生**（不通知机制、不进计数），所以它只会「白扔一张牌」。
>   可以在观察表里加一条：玩家会不会误以为召唤也计进了相生进度。

- 三个关卡各自只针对一个问题
- 每关我都写了「我的预测」—— 预测错了同样有价值，说明这套设计里有个我没看出来的东西
- 最后一节是**观察表**，玩的时候就记，别靠回忆

---

## 通用步骤

1. 菜单 **TapGJ ▸ 新建关卡（定义 + 预制体 + 加入目录）** ×3 → 得到 `Assets/Levels/Level_01/02/03`。
2. 每关在 Inspector 里按下面的表填。`levelId` 保持自动生成的 `level_01/02/03` 别改。
3. 填完先看 Inspector 下半部分 —— 必须是 **「✔ 没发现配置问题」**。
   如果报了别的，先别玩，把那段话发我（那说明我的配置或校验有问题）。
4. 有「机制组件」那一步的关卡（02、03），要先选中它的 `.prefab` 去 **Add Component**，
   否则 Level 03 会直接报「Custom 目标没有机制」。
5. 每关点 Inspector 上的 **「Play 这一关」**。

> 元素池 / 牌池是**多选下拉框**，勾选即可（不要当单选）。
> 角色分工：`ElementPool` = 本关**允许出现**什么；`layoutText` = **开局摆**什么。

## Level 01「引水」— 相生能不能被自己发现

**要回答的问题**：玩家在没人教的情况下，会不会发现「用水牌打金 = 把金变成水」？
如果发现不了 → 我们需要游戏内的提示/教学（这直接变成 P4 的 HUD 需求）。

### rules

| 字段 | 值 |
|---|---|
| displayName | `引水` |
| BoardWidth / BoardHeight | `6` / `6` |
| CreepsPerElement | `4`（本关用布局，这个值不生效） |
| MaxMoveSteps | `3` |
| InitialHandSize | `5` |
| HandLimit | `5` |
| MaxDiscardsPerRound | `5` |
| MaxCardsPerRound | `0`（不限） |
| BottleCapacity | `5` |
| RoundLimit | `6` |
| Goal | `WaterOnly`（全场只剩水元素） |
| ElementPool | 勾 **金、水** |
| CardPool | 勾 **水** |
| CardEffect | `CardAsVirtualElement`（默认） |
| useFixedSeed / fixedSeed | **勾上** / `20240607` |
| fixedInitialHand | 留空 |

### layoutText（直接粘贴，6 行 × 6 列，共 8 个金）

```
金..金..
......
.金..金.
..金..金
......
金..金..
```

**为什么不放水**：棋盘上全是金时，两只金相遇只是「同元素禁止移动」，什么都不会发生 ——
水必须由**玩家出牌**引入。所以这一关的第一个动作必然由玩家发起。

### 我的预测

- 会发现相生：手牌全是水牌，点金格是唯一能做的事，反馈又很明确。
- 但**发现之后就没有决策了**：每张水牌稳定把 1 个金变成水、再白送 1 个水。
- **棋盘会开始自己收敛**：一旦场上有了水，金撞上水（准备阶段小怪自己走）就会自动变水。
  玩家的作用快速下降 —— 这是我最想验证的一条。

### 玩的时候看什么

1. 第一次出牌前你犹豫了多久？有没有去点过空格 / 点过手牌想找说明？
2. 从「发现怎么玩」到「确定会赢」之间，你做过几个**真正的选择**？（0 个 = 目标太线性）
3. 水出现之后，是不是基本不用你动手了？（是 = 相生需要一个**对抗性力量**，正好指向 Level 02）
4. 6 回合上限有没有压力？（没有 = `RoundLimit` 对这类目标是无效的难度旋钮）

## Level 02「灭火」— 相克 + 定时加压

**要回答的问题**：`每 N 回合生成元素` 这种机制能不能制造出「追不上」的紧张感？
`每回合出牌上限` 是紧还是松？

### rules

| 字段 | 值 |
|---|---|
| displayName | `灭火` |
| BoardWidth / BoardHeight | `6` / `6` |
| MaxMoveSteps | `3` |
| InitialHandSize | `5` |
| HandLimit | `5` |
| MaxDiscardsPerRound | `5` |
| **MaxCardsPerRound** | **`3`**（这是本关的难度旋钮） |
| BottleCapacity | `5` |
| RoundLimit | `8` |
| **Goal** | `ElementAtMost`，Target = **火**，TargetCount = **`0`** |
| ElementPool | 勾 **金、水、火** |
| CardPool | 勾 **水** |
| useFixedSeed / fixedSeed | **勾上** / `20240607` |
| fixedInitialHand | 留空 |

### layoutText（6 行 × 6 列：4 火、1 金、1 水）

```
火...火.
......
..金...
...水..
......
.火...火
```

### 关卡预制体上的机制组件

选中 `Level_02.prefab` → **Add Component** → `Spawn On Round Rule`：

| 字段 | 值 |
|---|---|
| Element | `Fire`（火） |
| Every Rounds | `2` |
| Count Per Time | `1` |
| Announce | 勾上 |
| Goal Description | 留空 |

### 我的预测

- **水会滚雪球**：水牌打金是相生，会额外白送一个水；水越多越容易灭火 → 前 4 回合紧张，之后突然变简单。
- 3 张/回合可能刚好，也可能让你在第 3 回合就发现「无论如何都追不上」。

### 玩的时候看什么

1. 有没有出现**追不上**的时刻？还是反而中后期变得毫无压力？
2. 时间压力来自「火变多了」还是「牌不够用」？（两者指向完全不同的修改方向）
3. 目标显示成「火 0/≤0」你看得懂吗？进度条（`ElementAtMost` 是反着填的）有没有误导你？
4. 机制每 2 回合插一句「第 N 回合在 (x,y) 生成 1 个火元素」——
   它是**排队在动画序列里播**的。看它是否打断节奏 / 刷屏。
5. 3 张/回合：你是「刚好用完」还是「经常不够」还是「经常剩」？

## Level 03「相生计数」— 自定义目标的机制框架

**要回答的问题**：非消除类的目标（累计做事，而不是把棋盘弄成某个样子）好不好玩？
机制组件提供的进度条在 HUD 上够不够用？`Custom` 目标的配置流程顺不顺？

### rules

| 字段 | 值 |
|---|---|
| displayName | `相生计数` |
| BoardWidth / BoardHeight | `6` / `6` |
| MaxMoveSteps | `3` |
| InitialHandSize | `5` |
| HandLimit | `5` |
| MaxDiscardsPerRound | `5` |
| MaxCardsPerRound | `0`（不限） |
| BottleCapacity | `5` |
| RoundLimit | `12` |
| **Goal** | **`Custom`**（由关卡机制组件判定） |
| ElementPool | 勾 **金、水、木** |
| CardPool | 勾 **水、木** |
| useFixedSeed / fixedSeed | **勾上** / `20240607` |
| fixedInitialHand | 留空 |

### layoutText（6 行 × 6 列：金水木各 2 个）

```
金.....
..水...
....木.
.金....
....水.
木.....
```

### 关卡预制体上的机制组件

选中 `Level_03.prefab` → **Add Component** → `Reaction Count Rule`：

| 字段 | 值 |
|---|---|
| Target | `10` |
| Player Cards Only | **不勾**（小怪自己撞出来的相生也算） |
| Goal Description | 留空（会用默认的「累计完成 10 次相生转换」） |

### 我的预测

- **进度条会自己涨**：`Player Cards Only` 不勾，准备阶段小怪互相撞出的相生也会计数。
  你可能会觉得「我什么都没干它就涨了」。
- 勾上 `Player Cards Only` 再试一次，对比哪个更像"我在打一局游戏"。

### 玩的时候看什么

1. 进度条涨的时候，你能不能对应上**是哪次反应**造成的？（对不上 = 计数类目标需要反馈，不只是数字）
2. 换成勾上 `Player Cards Only` 再玩一次，哪个更像有计划的游戏？
3. 这个目标有没有让你产生**跨回合的计划**（攒某张牌 / 故意保留某个元素）？
4. `Custom` 的配置流程：先建关、再发现要挂组件、再去挂 —— 顺不顺？
   报错信息够不够直接？
5. **试着「刷」进度**：反复用同一张牌打同一个目标。
   出牌相生有两支 —— 「牌赢」时目标就地变成牌面元素（真的转换了），
   「目标赢」时目标**没变**、只是在旁边多生成一只。现在的计数把两支都算进去了。
   如果你发现可以靠反复打同一种牌把进度刷满，那就是这个计数定义太宽了
   —— 这条我算是提前告诉你了，验证一下是不是真的能刷。

## 回来之后怎么汇报

每关三句话就够：

1. **实际发生了什么**（和我的预测哪里不一样？）
2. **你什么时候觉得无聊 / 觉得紧**（第几回合、什么状态下）
3. **你当时想看但看不到的信息**（原文记下来）

有了这三样，我才能判断下一步该做：卡牌定义层（新卡牌）、反应表按关卡覆盖（新规则）、
还是 P4 的 HUD —— 而不是拍脑袋选一个。
